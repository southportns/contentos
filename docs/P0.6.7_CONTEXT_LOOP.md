# P0.6.7 — End-to-End Context Loop

## 1. Mission

建立 ContextOS 第一版 End-to-End Context Loop。将 Decision Memory、Outcome Memory、Decision Feedback、Context Graph、Context Assembly 和 Learning Candidate 生成串联成一个完整的、可观测的管道。

核心目标：修复 `learningCandidates` 为 0 的问题，确保 Decision → Outcome → Feedback → Learning 链路在测试中正确运行。

## 2. Architecture Diagram

```
ContextLoopRequest
      ↓
runContextLoop()
      │
      ├─[1] Validate Request (ownerId, decisionId)
      │
      ├─[2] Retrieve Decision (getDecisionById — O(1) exact-id lookup)
      │     └─ MemoryNotFoundError if not found or wrong owner
      │
      ├─[3] Build Decision Feedback
      │     ├─ Retrieve Outcomes attributed to Decision
      │     ├─ Aggregate Metrics & Trends
      │     ├─ Resolve Time Window [decision.createdAt, now]
      │     └─ Retrieve OutcomeMemory[] for Context conversion
      │
      ├─[4] Resolve Graph Context (getGraphContext — OPTIONAL)
      │     ├─ traverseContextGraph() from Decision node
      │     └─ Returns related ContextObjects (empty if no graph)
      │
      ├─[5] Build Context Collection
      │     ├─ Decision → ContextObject (via decisionMemoryToContext)
      │     ├─ Outcome(s) → ContextObject(s) (via outcomeMemoryToContext)
      │     ├─ Feedback → ContextObject (via decisionFeedbackToContext)
      │     └─ Graph Contexts → ContextObjects (optional)
      │
      ├─[6] Assemble Context (assembleContexts — Dedup→Select→Rank→Budget)
      │
      ├─[7] Generate Learning Candidates (buildLearningCandidates)
      │     ├─ No outcomes → [] (no false learning)
      │     ├─ Trend analysis → successful_pattern / failure_pattern
      │     ├─ Metric thresholds → strategy_signal
      │     └─ Decision-action pairs → decision_pattern
      │
      ├─[8] (Optional) Persist Learning Candidates
      │     └─ persistLearningCandidate callback (if provided)
      │
      └─ Return ContextLoopResult
```

**Pipeline Data Flow:**

```
Decision
   ↓
Outcome
   ↓
Feedback
   ↓
┌───────────────────────┐
│ Context Inputs        │
│                       │
│ Decision Context      │
│ Outcome Context(s)    │
│ Decision Feedback Ctx │
│ Graph Context(s)      │ ← OPTIONAL
└───────────┬───────────┘
            ↓
   Context Assembly
            ↓
  Learning Candidate
            ↓
   Optional Memory
```

## 3. Pipeline Stages

| Stage | Input | Output | Fatal on Failure |
|-------|-------|--------|-----------------|
| 1. Validation | ContextLoopRequest | void/throw | YES |
| 2. Decision Retrieval | ownerId, decisionId | DecisionMemory | YES (MemoryNotFoundError) |
| 3. Feedback Build | Decision + params | DecisionFeedback | No (null if no outcomes) |
| 4. Graph Traversal | Graph + nodeId | ContextObject[] | No (empty if no graph) |
| 5. Collection Build | All sources | ContextObject[] | No |
| 6. Assembly | Contexts | ContextAssemblyResult | No (empty result) |
| 7. Learning | Decision + Feedback | LearningCandidate[] | No (empty if no evidence) |
| 8. Persistence | Candidates | void | No |

## 4. Loop Completeness

```
'no_decision'        → Decision not found
'no_outcome'         → Decision found, no outcomes attributed
'outcome_available'  → Outcomes exist, feedback not built
'feedback_available' → Feedback built, no assembly/graph yet
'graph_available'    → Graph produced contexts, no assembly yet
'assembled'          → Assembly completed, no learning candidates
'learned'            → Learning Candidates generated
```

### 4.1 Graph is OPTIONAL — Not a Hard Prerequisite

Graph traversal is **enrichment only**. It does NOT block Assembly or Learning.

| Decision | Outcome | Feedback | Graph | Assembly | Learning | → Completeness |
|----------|---------|----------|-------|----------|----------|----------------|
| ✓ | ✓ | ✓ | ✗ | ✓ | ✓ | **`learned`** |
| ✓ | ✓ | ✓ | ✗ | ✓ | ✗ | **`assembled`** |
| ✓ | ✓ | ✓ | ✗ | ✗ | ✗ | **`feedback_available`** |
| ✓ | ✓ | ✓ | ✓ | ✗ | ✗ | **`graph_available`** |
| ✓ | ✓ | ✓ | ✓ | ✓ | ✗ | **`assembled`** |
| ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | **`learned`** |
| ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | **`no_outcome`** |
| ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | **`no_decision`** |

### 4.2 Logic

```typescript
if (!decision) return 'no_decision';
if (!outcome)  return 'no_outcome';
if (!feedback) return 'outcome_available';

// Learning is the furthest possible stage
if (learning)  return 'learned';

// Assembly occurred (possibly without graph)
if (assembly)  return 'assembled';

// Graph enrichment occurred but no assembly attempted
if (graph)     return 'graph_available';

// Feedback built but no graph/assembly/learning
return 'feedback_available';
```

### 4.3 Rationale

- **Outcome is required for Learning** — no evidence → no candidates (no false learning)
- **Graph only adds extra contexts** — its absence does not affect core pipeline
- **Assembly depends only on having contexts** — Decision + Outcome + Feedback are enough

## 5. Canonical Outcome Evidence

### 5.0 Architecture Invariant

**Decision Feedback is the canonical resolver of the Outcome evidence window.**

Outcome Contexts added to Context Assembly MUST be derived from the same `[windowStart, windowEnd)` resolved by Decision Feedback.

```
Decision
   ↓
Decision Feedback
   ↓
Canonical Outcome Window
   ├──────────────→ Outcome Contexts
   │
   └──────────────→ Aggregation / Trend
```

This guarantees that Feedback, Aggregation, Trend, and Outcome Context all consume the **same** Outcome evidence set within a single Context Loop execution.

### 5.0.1 Why Feedback Window Is Canonical

Feedback builder applies default window resolution (`[decision.createdAt, now]`) when explicit `windowStart`/`windowEnd` are not provided. The raw `request.windowStart`/`request.windowEnd` do NOT carry this default resolution.

Therefore, using `request.windowStart`/`request.windowEnd` for Outcome Context retrieval would:
- Include outcomes before the decision (when no explicit windowStart)
- Exclude valid outcomes within the actual computation window

The orchestrator uses `feedback.windowStart` and `feedback.windowEnd` (not `request.windowStart`/`request.windowEnd`) as the canonical time source.

### 5.0.2 Retrieval Limit Alignment

Outcome Context retrieval uses the same `retrievalLimit` as Feedback:
```
limit: request.retrievalLimit ?? 500
```

The actual clamping continues to be handled by the existing Outcome Retrieval internals.

### 5.0.3 Do Not Reimplement Retrieval

The Context Loop continues to reuse `retrieveDecisionOutcomes()` — it does NOT:
- Directly query Prisma from the Loop
- Directly access MemoryStore from the Loop
- Implement manual outcome filtering

All scope isolation (owner, project, topic) and `[windowStart, windowEnd)` filtering remain the responsibility of Decision Feedback / Outcome Retrieval.

## 6. Context Sources

The Assembly pipeline receives context from **four sources**:

### 5.1 Decision Context

```
DecisionMemory → decisionMemoryToContext() → ContextObject<DecisionContextPayload>
ID: ctx_dec_${decisionId}
```

Always present (when Decision is found).

### 5.2 Outcome Context(s)

```
OutcomeMemory[] → outcomeMemoryToContext() → ContextObject<OutcomeContextPayload>
ID: ctx_out_${outcomeId}
```

**Always present when outcomes exist.** Uses `retrieveDecisionOutcomes()` to get
OutcomeMemory[] (reuses existing attribution/scope/time-window filtering), then
converts each via `outcomeMemoryToContext()`. Each Outcome gets its own Context.

### 5.3 Decision Feedback Context

```
DecisionFeedback → decisionFeedbackToContext() → ContextObject<DecisionFeedbackContextPayload>
ID: dfb_${decisionId}
```

Present when feedback is built (outcomes attributed).

### 5.4 Graph Context(s)

```
ContextGraph → getGraphContext() → ContextObject[]
Node-specific IDs
```

**Optional enrichment.** When no graph is provided, Graph Contexts are skipped.
The pipeline continues normally without them.

### 5.5 Context Deduplication

All contexts pass through `deduplicateContextsById()` before Assembly:
```
Decision Context
Outcome Context(s)    ← NEW in P0.6.7-R1
Decision Feedback Ctx
Graph Context(s)      ← optional
       ↓
deduplicateContextsById()
       ↓
Assembly Pipeline (Select→Rank→Budget)
```

## 7. Learning Candidates

### 7.1 Candidate Types

| Type | Trigger Condition | Source Evidence |
|------|-------------------|-----------------|
| `decision_pattern` | Decision-action pair observed | Decision context + action |
| `successful_pattern` | ≥60% metrics trending up | Trend analysis |
| `failure_pattern` | ≥60% metrics trending down | Trend analysis |
| `strategy_signal` | High metric value (>1000) | Metric aggregation |
| `preference_signal` | Repeated similar decisions | Decision history |

### 7.2 Design Rules

1. **No outcomes = no candidates** — prevents false learning
2. **Confidence bounded** — candidate.confidence ≤ min(decision.confidence, feedback.confidence)
3. **Bounded feedback degrades confidence** — incomplete evidence → lower confidence
4. **Evidence chain preserved** — each candidate records its source Decision, Outcomes, and Feedback IDs
5. **Deterministic IDs** — `lc_${decisionId}_${type}` (no UUID/random)
6. **Candidates ≠ Knowledge** — candidates are hypotheses, not confirmed truths

### 7.3 Thresholds

```typescript
const HIGH_METRIC_THRESHOLD = 1000;  // Strong signal threshold
const POSITIVE_TREND_RATIO = 0.6;    // 60%+ up = successful
const NEGATIVE_TREND_RATIO = 0.6;    // 60%+ down = failure
const MIN_CONFIDENCE_FLOOR = 0.1;   // Minimum confidence floor
```

## 8. Dependencies (DI Pattern)

```typescript
interface ContextLoopDependencies {
  memoryRetriever: MemoryRetriever;           // Required: retrieve Decision + Outcomes
  decisionFeedbackBuilder?: DecisionFeedbackService;  // Optional: custom feedback builder
  graphTraverser?: Function;                  // Optional: custom graph traversal
  persistLearningCandidate?: Function;        // Optional: persist candidates
  now?: () => string;                         // Optional: deterministic clock
}
```

All dependencies are injected — no module-level singletons. This enables:
- Unit testing with InMemoryRetriever
- Deterministic testing with fixed `now`
- Custom feedback builders for testing
- Optional persistence (no side effects by default)

## 9. Determinism Guarantees

| Aspect | Guarantee |
|--------|--------|
| Loop ID | `loop_${decisionId}` — deterministic |
| Learning Candidate IDs | `lc_${decisionId}_${type}` — deterministic |
| Feedback window | Resolved from `decision.createdAt` and `now()` — deterministic with fixed `now` |
| Context Assembly | Deterministic for same input contexts |
| Decision Factory | Honors `createdAt` parameter (not wall-clock) |
| Lifecycle timestamps | `updatedAt` injected via `now()` — not wall-clock |

Non-deterministic fields (excluded from equality checks):
- `generatedAt` — execution metadata only
- `metrics.totalMs` — wall-clock timing
- `lifecycle.updatedAt` in constructed contexts

## 10. Owner Isolation

Owner isolation is enforced at EVERY stage:

1. **Decision Retrieval** — `getDecisionById` checks `ownerId`
2. **Feedback Building** — Outcomes filtered by `ownerId`
3. **Graph Context** — Only same-owner contexts traversed (via graph scope rules)
4. **Learning Candidates** — Each candidate carries `ownerId`
5. **Persistence** — `ownerId` passed to persist function

Cross-owner Outcomes attributed to a Decision belonging to another owner are NOT included in that owner's feedback.

## 11. Time Window Resolution

```
Case 1: windowStart + windowEnd provided → use as-is
Case 2: decision.createdAt + now        → default window
Case 3: windowStart only                → windowStart to now
Case 4: windowEnd only                  → decision.createdAt to windowEnd
```

Validation: `windowStart < windowEnd` (strict inequality).

## 13. Bug Fixes in P0.6.7

### 11.1 Decision Factory Timestamp Passthrough

**Problem**: `createDecisionMemory` did not forward `createdAt`/`updatedAt`/`expiresAt` from options. Factory always used `Date.now()`, so Decision creation time ≈ feedback request time → `windowStart === windowEnd` → validation error.

**Fix**: `decision-memory-factory.ts` — pass through `createdAt`, `updatedAt`, `expiresAt` from options to `createMemoryRecord`.

### 11.2 Lifecycle State updatedAt Injection

**Problem**: `createInitialLifecycleState()` used `new Date().toISOString()`, making it wall-clock dependent and non-deterministic.

**Fix**: `context-lifecycle.ts` — optional `updatedAt` parameter for deterministic lifecycle creation.

### 11.3 Deterministic Feedback Generation

**Problem**: `buildDecisionFeedback` and entry point used `new Date().toISOString()` for `requestedAt`, making feedback non-deterministic across runs.

**Fix**: Added `now` provider to `DecisionFeedbackParams` threaded from Orchestrator's `dependencies.now()`.

### 11.4 Cross-Project Scope in Tests

**Problem**: `runE2E` used Project A's scope, but `Cross-Project Isolation` test created Decision + Outcome under different projects → scope mismatch → 0 outcomes in feedback.

**Fix**: E2E test directly calls `runContextLoop` with correct `projectId`/`topicId`.

## 14. Design Invariants

| Invariant | Enforcement |
|-----------|-------------|
| Loop = orchestration only | Delegates to existing subsystems |
| Same input → same output | All IDs deterministic, `now` injectable |
| Partial > failure | Non-fatal stages degrade gracefully |
| No Decision/Outcome mutation | Read-only access to MemoryRecords |
| No Knowledge mutation | Candidates returned, not auto-persisted |
| No LLM / No causal inference | Evidence-only candidate derivation |
| Owner isolation at every stage | Checked in retrieval, feedback, learning |
