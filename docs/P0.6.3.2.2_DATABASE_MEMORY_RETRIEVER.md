# P0.6.3.2.2 — Database Memory Retriever

**Status**: PASS
**Date**: 2026-09-30
**Author**: ContentOS Team

## 1. Overview

This phase adds a production-grade database-backed memory retriever to the Memory Layer. It translates `MemoryRetrievalRequest` into a structured database query (`MemoryQueryCriteria`), executes it through the `MemoryStore` interface, and returns filtered, sorted `MemoryRecord[]` results.

## 2. Architecture

**Data Flow**:
```
MemoryRetrievalRequest
        ↓
DatabaseMemoryRetriever
  • Validates ownerId (required)
  • Resolves scope (explicit > inferred)
  • Maps policy to criteria
        ↓
MemoryQueryCriteria (DB query DTO)
  • ownerId, projectId, topicId
  • allowedScopes, status, kinds
  • minConfidence, minImportance
  • updatedAfter, take
        ↓
MemoryStore.findMany(criteria)  [interface]
        ↓
PrismaMemoryStore
  • buildWhereClause() → Prisma OR conditions
  • ORDER BY importance, confidence, updatedAt, id
  • LIMIT (take)
        ↓
PrismaClient → SQLite
        ↓
MemoryRecord[]
```

**Relationship to MemoryRetriever**:
```
MemoryRetriever (interface)
├── InMemoryRetriever (preserved, P0.6.3.1)
└── DatabaseMemoryRetriever (new, P0.6.3.2.2)
```

### Key Design Decisions

1. **Layered abstraction**: Retriever → Criteria → Store → Prisma → DB
2. **ownerId enforced at TWO levels**: retriever (pre-flight) + database (WHERE clause)
3. **Scope isolation via OR conditions**: global always, project by match, topic by match
4. **All filtering at database level**: no application-layer post-filtering for security
5. **Deterministic sorting**: importance → confidence → updatedAt → id (tie-breaker)

## 3. Security Model

### ownerId Isolation

- **Mandatory field**: `ownerId` MUST be provided or `MemoryRetrievalError` is thrown
- **Database WHERE clause**: Every query includes `ownerId = ?` — enforced at DB level
- **No bypass**: Records from other users are NEVER returned, even if projectId/topicId match

### Cross-Project Isolation

- Global memories: always available within owner boundary
- Project memories: only records matching `projectId = request.projectId`
- Topic memories: only records matching `projectId = request.projectId AND topicId = request.topicId`

### Cross-Topic Isolation

- Topic records require BOTH projectId AND topicId to match
- Same project, different topic → EXCLUDED

## 4. Scope Behavior

### Scope Inference Rules

| Request Context | Allowed Scopes (effective) |
|---|---|
| `scope: 'global'` (explicit) | `['global']` |
| `scope: 'project'` (explicit) | `['project']` |
| `scope: 'topic'` (explicit) | `['topic']` |
| `projectId` + `topicId` | `['global', 'project', 'topic']` |
| `projectId` only | `['global', 'project']` |
| neither | `['global']` |

### Explicit Scope Priority

When `request.scope` is set, it takes priority over inferred scope from IDs. This allows callers to narrow retrieval to a single scope.

### Policy allowedScopes

When `policy.allowedScopes` is set, it further constrains the effective scopes through intersection:

```
effectiveScopes = inferredScopes ∩ policy.allowedScopes
```

**Example**: If context allows `['global', 'project', 'topic']` but policy says `['global']`, only global records are returned.

### Session Scope

Session-scope memories are **never** included in persistent retrieval. They are ephemeral by design.

## 5. Filtering

### Scope Filtering
- Implemented via `OR` conditions in Prisma `where` clause
- Each scope type adds specific conditions:
  - `global`: `{ scope: 'global' }`
  - `project`: `{ scope: 'project', projectId: ? }`
  - `topic`: `{ scope: 'topic', projectId: ?, topicId: ? }`

### Status Filtering

| Status | Default | With Flag |
|---|---|---|
| `active` | Included | Included |
| `expired` | Excluded | `includeExpired: true` |
| `superseded` | Excluded | `includeSuperseded: true` |
| `archived` | NEVER | NEVER |

Single status → `status = 'value'`
Multiple statuses → `status: { in: ['active', 'expired'] }`

### Confidence Filtering
- `minConfidence` → Prisma `confidence: { gte: value }`
- Default: `0.3` (from `DEFAULT_MEMORY_POLICY`)

### Importance Filtering
- `minImportance` → Prisma `importance: { gte: value }`
- Default: `0` (no importance filtering)

### Kind Filtering
- `allowedKinds` → Prisma `kind: { in: [...] }`
- `excludedKinds` → Prisma `kind: { notIn: [...] }`
- Both can be combined (intersection)

### Age Filtering (maxAgeDays)
- Computed as: `updatedAfter = now - maxAgeDays * 24h`
- Applied as Prisma: `updatedAt: { gte: updatedAfter }`

**Consistent with InMemoryRetriever**: Both use the same `maxAgeDays` policy field, ensuring behavior alignment.

## 6. Ranking

### Sort Order (deterministic)

```
ORDER BY
  importance DESC,    -- Primary: most important first
  confidence DESC,    -- Secondary: most reliable first
  updatedAt DESC,     -- Tertiary: most recently updated first
  id ASC              -- Tie-breaker: stable alphabetical order
```

### Why This Order?

1. **importance**: User/system-assigned priority (most meaningful signal)
2. **confidence**: Reliability indicator (high confidence = trustworthy)
3. **updatedAt**: Recency (freshness matters for context)
4. **id**: Deterministic tie-breaking (same sort every time)

## 7. API Reference

### MemoryQueryCriteria

```typescript
interface MemoryQueryCriteria {
  ownerId: string;               // REQUIRED — owner isolation
  projectId?: string;            // Filter by project
  topicId?: string;              // Filter by topic
  scope?: MemoryScope;           // Explicit scope override
  allowedScopes?: MemoryScope[]; // Scope allowlist
  kinds?: MemoryKind[];          // Kind allowlist
  excludedKinds?: MemoryKind[];  // Kind blocklist
  status?: MemoryStatus[];       // Status filter (default: ['active'])
  minConfidence?: number;        // Confidence threshold
  minImportance?: number;        // Importance threshold
  updatedAfter?: Date;           // Age cutoff
  take?: number;                 // LIMIT
}
```

### DatabaseMemoryRetriever

```typescript
class DatabaseMemoryRetriever implements MemoryRetriever {
  constructor(store: MemoryStore);
  retrieve(request: MemoryRetrievalRequest): Promise<MemoryRecord[]>;
}
```

### MemoryStore.findMany()

```typescript
interface MemoryStore {
  // ... existing methods ...
  findMany(criteria: MemoryQueryCriteria): Promise<MemoryRecord[]>;
}
```

## 11. Non-Goals (explicitly NOT implemented)

- No semantic/embedding/vector search
- No Writing integration (memory → prompt)
- No Context Assembly integration
- No LLM memory extraction/summarization/merging
- No session-scope persistence retrieval
- No real-time notification on memory changes

## 12. Known Limitations

1. **Session scope**: Session memories are excluded from persistent retrieval (by design)
2. **Archived records**: Always excluded, no flag to include them
3. **No full-text search**: Query string field exists on `MemoryRetrievalRequest` but not yet implemented
4. **No OFFSET pagination**: Only `take` (LIMIT) is supported; no skip/cursor pagination
