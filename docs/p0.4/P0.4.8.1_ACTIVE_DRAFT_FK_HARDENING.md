# P0.4.8.1 — Active Draft Foreign Key Hardening

**Status**: COMPLETED
**Date**: 2026-09-22
**Author**: CatPaw AI (southportns/contentos)
**Prerequisite**: P0.4.8 (Active Draft / Current Version)

## 1. Overview

P0.4.8 在 `Topic.activeDraftId` 列和 `Draft.id` 之间建立了 Prisma `@relation`，但实际 SQLite 数据库中**缺少外键约束**。这意味着引用完整性完全依赖应用层逻辑。

P0.4.8.1 在数据库层面添加了缺失的 FK 约束，确保：
- 不能将 `activeDraftId` 指向不存在的 Draft
- 删除 Draft 时自动 `SET NULL`
- 保持 `@unique` 约束（一个 Draft 不能同时是两个 Topic 的 active draft）

## 2. Problem Statement

### 2.1 Schema vs Database Drift

Prisma schema 定义了关系：
```prisma
model Topic {
  activeDraftId String?   @unique
  activeDraft   Draft?    @relation("TopicActiveDraft", fields: [activeDraftId], references: [id], onDelete: SetNull)
}
```

但 `PRAGMA foreign_key_list('Topic')` 确认 SQLite 中**没有 activeDraftId 的外键**。

### 2.2 Root Cause

P0.4.8 的 migration (`20260922170000_add_topic_active_draft`) 只添加了列和普通索引：
```sql
ALTER TABLE "Topic" ADD COLUMN "activeDraftId" TEXT;
CREATE INDEX "Topic_activeDraftId_idx" ON "Topic"("activeDraftId");
```

未包含 FK 约束创建语句——SQLite 不支持 `ALTER TABLE ADD CONSTRAINT` 添加 FK。

### 2.3 Risk Without FK

应用层虽有 protection（cross-topic check），但：
- 直接 SQL 操作（admin, migration, 手动修复）可能创建孤立引用
- Race condition 下可能两个 Topic 指向同一个 Draft（绕过 @unique）
- 删除 Draft 后 Topic 仍持有废弃 ID，fallback 逻辑可能无法正常工作

## 3. Solution

### 3.1 SQLite Table-Rebuild Pattern

SQLite 不支持 ALTER TABLE ADD CONSTRAINT 创建 FK，使用标准表重建模式：

```sql
PRAGMA foreign_keys=OFF;
BEGIN TRANSACTION;

-- 创建新表（包含 FK）
CREATE TABLE "new_Topic" (
  ...,
  "activeDraftId" TEXT,
  CONSTRAINT "new_Topic_activeDraftId_fkey" 
    FOREIGN KEY ("activeDraftId") REFERENCES "Draft" ("id") 
    ON DELETE SET NULL ON UPDATE CASCADE
);

-- 复制数据
INSERT INTO "new_Topic" (...) SELECT ... FROM "Topic";

-- 替换旧表
DROP TABLE "Topic";
ALTER TABLE "new_Topic" RENAME TO "Topic";

-- 重建索引
CREATE INDEX "Topic_activeDraftId_idx" ON "Topic"("activeDraftId");
CREATE UNIQUE INDEX "Topic_activeDraftId_key" ON "Topic"("activeDraftId");

COMMIT;
PRAGMA foreign_keys=ON;
```

### 3.2 Migration File

`prisma/migrations/20260922171000_harden_topic_active_draft_foreign_key/migration.sql`

### 3.3 Why Table Rebuild?

SQLite 的 ALTER TABLE 能力有限：
- ✅ `ADD COLUMN`（无 FK/UNIQUE 限制的列）
- ❌ `ADD CONSTRAINT FOREIGN KEY`
- ❌ `ADD CONSTRAINT UNIQUE`
- ❌ `ALTER COLUMN`

唯一方式是创建新表、复制数据、替换旧表。

### 3.4 Safety Measures

1. **PRAGMA foreign_keys=OFF**: 防止 DROP TABLE 时级联行为破坏子表 FK 引用
2. **BEGIN TRANSACTION / COMMIT**: 原子操作，任何步骤失败回滚
3. **data copy**: 全部数据保持不变
4. **索引重建**: 全部原始索引 + 新增 unique index
5. **不修改历史 migration**: 遵循项目原则

## 6. Design Decisions

### 6.1 Why Not `prisma migrate dev --create-only`?

Prisma detected pre-existing drift (Humanization table redefinition, UserContentArchive extra columns) — these are baseline issues unrelated to P0.4.8.1. Using `--create-only` would require `prisma migrate reset` which is prohibited.

### 6.2 Why Manual Migration?

`prisma migrate diff --from-url` was removed in newer Prisma versions. Manual SQL gives precise control over the SQLite table-rebuild pattern.

### 6.3 Why PRAGMA foreign_keys=OFF During Rebuild?

Without this, DROP TABLE "Topic" would trigger cascade behaviors from child tables (Draft, Evaluation, etc.) that reference Topic. Disabling FKs ensures clean replacement. Re-enabled after COMMIT.

### 6.4 Why UNIQUE INDEX Separate from FK?

FK ensures Draft exists. UNIQUE ensures Draft is active for at most one Topic. Both required for Prisma's `@unique` semantics at the DB level.

## 8. Risk Assessment

| Risk | Mitigation |
|------|------------|
| Data loss during table rebuild | Transaction wrapping + backup before apply |
| Drift blocks Prisma CLI | Manual SQL migration (no reset) |
| FK breaks existing app layer | P0.4.8 app logic already enforces same rules |
| Performance impact from new index | Unique index is same btree as existing regular index |
