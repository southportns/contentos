## 1. ContextOS Definition

### 1.1 Core Identity

**ContextOS = Context Operating System**

ContextOS is the infrastructure layer that manages the complete lifecycle of context for Agent execution:

```
Capture → Normalize → Store → Retrieve → Assemble → Apply → Evaluate → Learn → Update
```

### 1.2 What ContextOS Is NOT

ContextOS is **NOT**:

| Not | Why |
|-----|-----|
| AI Writer | Writing is a Skill that consumes Runtime Context |
| Chatbot | Conversational behavior is Agent responsibility |
| Single Agent | Runtime serves any Agent, any number of times |
| Knowledge Base | Knowledge is a source; Runtime orchestrates retrieval |
| Prompt Manager | Rendering is Assembly output, not Runtime core |

### 1.3 Core Mandate

> ContextOS is responsible for providing the **correct, traceable, reusable, and learnable** context to an Agent during a single task execution.

### 1.4 Three-Layer Separation

| Layer | Question | Responsibility |
|-------|----------|----------------|
| **Memory** | "What does the system remember?" | Persistent state store |
| **Context** | "What does the current task need to know?" | Task-specific information selection |
| **Runtime** | "How does the current Agent obtain, use, and feedback this information?" | Execution orchestration |

## 2. Runtime Responsibility

### 2.1 Primary Responsibilities

ContextOS Runtime is responsible for:

1. **Receiving** a ContextOS Runtime Request
2. **Determining** what Context the task needs
3. **Calling** existing Retrieval capabilities
4. **Calling** Context Assembly
5. **Forming** an Agent Context Package
6. **Recording** which Contexts were used in this Agent Run
7. **Receiving** Agent Decisions / Actions / Outputs
8. **Receiving** Outcomes / Feedback
9. **Generating** Learning Candidates
10. **Deciding** (via Policy) whether to persist into Memory

### 2.2 Responsibility Matrix

| Concern | Runtime | Agent | Skill | Tool | Memory |
|---------|---------|-------|-------|------|--------|
| Context Retrieval | **Yes** | No | No | No | Provides |
| Context Assembly | **Yes** | No | No | No | Provides |
| Context Injection | **Yes** | Consumes | No | No | No |
| Agent Run Tracking | **Yes** | Executes | No | No | No |
| Decision Recording | **Yes** | Produces | No | No | Stores |
| Outcome Evaluation | **Yes** | Reports | No | No | Stores |
| Learning Generation | **Yes** | No | No | No | Stores |
| Memory Persistence | Orchestrates | No | No | No | **Yes** |

## 4. Runtime Request

### 4.1 ContextOSRuntimeRequest

```typescript
interface ContextOSRuntimeRequest {
  /** Owner (user) ID — mandatory for isolation */
  ownerId: string;

  /** Project scope (optional) */
  projectId?: string;

  /** Topic scope (optional) */
  topicId?: string;

  /** Task/Run identifier (optional, for tracking) */
  taskId?: string;

  /** Input data for the Agent — structure defined by Agent, not Runtime */

```

### 4.2 Business Agnostic Principle

**CRITICAL**: Runtime MUST remain business-agnostic.

**PROHIBITED** — Hardcoding business objects into Runtime:

- ~~`douyinTopic`~~
- ~~`contentDraft`~~
- ~~`viralScore`~~

The Runtime's `input: unknown` and `purpose: string` are the ONLY contracts. Business-specific structures are the Agent's responsibility to interpret.

### 4.3 Purpose vs. Input

| Field | Role | Defined By |
|-------|------|------------|
| `purpose` | Why is this run happening? | Agent Contract |
| `input` | What data does the Agent need? | Agent Contract |
| `ownerId` | Whose data? | Runtime Mandatory |
| `projectId` / `topicId` | Scope boundary | Runtime Mandatory |

## 5. Context Policy

### 5.1 ContextOSContextPolicy

```typescript
interface ContextOSContextPolicy {
  /** Maximum estimated tokens for context injection */
  maxTokens?: number;

  /** Maximum number of context objects */
  maxContexts?: number;

  /** Allowed context kinds (whitelist) */
  allowedKinds?: ContextKind[];

  /** Excluded context kinds (blacklist) */
  excludedKinds?: ContextKind[];

  /** Allowed memory scopes for retrieval */
  allowedScopes?: MemoryScope[];

  /** Whether to include graph-related contexts */
  includeGraph?: boolean;

  /** Maximum graph traversal depth */
  graphDepth?: number;

  /** Whether to include memory contexts */
  includeMemory?: boolean;

  /** Whether to include outcome contexts */
  includeOutcomes?: boolean;

  /** Whether to include decision contexts */
  includeDecisions?: boolean;

  /** Whether to include feedback contexts */
  includeFeedback?: boolean;
}
```

### 5.2 Policy Semantics

Policy controls **how much** context ContextOS should provide to the Agent.

| Policy | Effect |
|--------|--------|
| `maxTokens` | Hard cap on serialized context size |
| `maxContexts` | Hard cap on number of context objects |
| `allowedKinds` | Restrict info categories (e.g., strategy only) |
| `allowedScopes` | Restrict scope (e.g., global + project, no topic) |
| `includeGraph` | Enable/disable graph-based context enrichment |
| `includeMemory` | Enable/disable episodic/semantic memory retrieval |
| `includeOutcomes` | Enable/disable outcome history |
| `includeDecisions` | Enable/disable decision history |
| `includeFeedback` | Enable/disable decision feedback |

### 5.3 Default Policy

When `contextPolicy` is not provided, Runtime uses a sensible default:
- Include memory, outcomes, decisions, feedback
- No graph (graphDepth = 0)
- maxTokens from global configuration
- All scopes allowed (within owner boundary)

- Memory Retrieval
- Decision Retrieval
- Outcome Retrieval
- Knowledge Retrieval
- Graph Retrieval
- Context Retrieval

### 6.2 Retrieval Flow

```
ContextOSRuntimeRequest
        ↓
retrieveRuntimeContext()
        ↓
    ┌───┴───┐
    ↓       ↓
 Memory   Context
 Retrieval  Retrieval
    ↓       ↓
    └───┬───┘
        ↓
```

### 6.3 Agent Isolation Principle

> **The Agent MUST NOT know which internal retrieval systems exist.**

The Agent receives a `RuntimeContextPackage` — the RESULT of retrieval, not the retrieval process.

Internal retrieval systems may change (add vector DB, remove graph, etc.) without any Agent code change.

## 14. Security / Isolation

### 14.1 Inherited from P0.6

Runtime **INHERITS** all P0.6 security guarantees:

- Owner Isolation
- Project Isolation
- Topic Isolation
- Scope Resolution

### 14.2 Owner-First Principle

Every Runtime Retrieval **MUST** carry `ownerId`.

**PROHIBITED**:
```typescript
// WRONG — filter at application layer
const all = await retrieveAllMemory();
return all.filter(m => m.ownerId === ownerId);
```

**REQUIRED**:
```typescript
// CORRECT — filter at data layer
return await retrieveMemory({ ownerId, ... });
```

### 14.3 Security Boundary

> **Security boundary MUST be enforced BEFORE Context Assembly.**

```
Retrieval (owner-scoped)
      ↓
Context Objects (already filtered)
      ↓
Assembly (works only with what's available)
      ↓
Package (only contains authorized contexts)
```

### 14.4 Isolation Matrix

| Boundary | Enforcement |
|----------|-------------|
| Owner | Every query: `ownerId = ?` |
| Project | Scope filter in retrieval |
| Topic | Scope filter in retrieval |
| Scope | `PersistentMemoryScope` excludes session |

## 15. Determinism

### 15.1 Determinism Guarantee

ContextOS Runtime **MUST** support:

```
same input
  + same context state
  + same now
  = same runtime context
```

### 15.2 Injectable Clock

```typescript
interface ContextOSRuntimeDependencies {
  /**
   * Clock function for deterministic timestamps.
   * Default: () => new Date().toISOString()
   */
  now?: () => string;
}
```

### 15.3 Prohibited Patterns

In Runtime core logic:

| Prohibited | Allowed |
|------------|---------|
| `new Date()` directly | Via `now()` injection |
| `Math.random()` | Deterministic ID generation |
| `crypto.randomUUID()` | Pattern-based IDs (e.g., `run_${purpose}_${timestamp}`) |

**Exception**: Infrastructure layer (Prisma, system utilities) may use these for operational concerns, NOT business logic.

### 15.4 Deterministic ID Patterns

| Entity | Pattern |
|--------|---------|
| Run | `run_${ownerId}_${timestamp}` |
| Context Usage | `cu_${runId}_${contextId}` |

### 15.5 Deterministic Clock Wiring (P0.7.1-R1)

The injected `now()` clock MUST propagate through the entire Runtime call chain:

```
Runtime Clock (now)
        ↓
runContextOS.now
        ↓
assembleRuntimeContext.now
```

**Implementation**:

```typescript
// createRuntimeRunner propagates clock to both runContextOS and assembleRuntimeContext
export function createRuntimeRunner(
  memoryRetriever: MemoryRetriever,
  now: () => string = () => new Date().toISOString(),
) {
  return async (request: ContextOSRuntimeRequest) => {
    return runContextOS(request, {
      retrieveContext: (req) => retrieveRuntimeContext(req, { memoryRetriever }),
      assembleContext: (contexts, policy, purpose) =>
        assembleRuntimeContext(contexts, policy, purpose, now),
      now,  // ← same clock for run timestamps
    });
  };
}
```

**Guarantee**: With a constant clock, `run.startedAt === run.completedAt === contextPackage.generatedAt`.

### 15.6 Runtime Scope Policy (P0.7.1-R1)

Runtime Retrieval interprets `allowedScopes` from `ContextOSContextPolicy` as follows:

| allowedScopes | Behavior |
|---------------|----------|
| `undefined` / `[]` | No scope param — MemoryRetriever resolves scope natively |
| `[single]` | Pass that single scope to MemoryRetriever |
| `[multiple]` | Per-scope retrieval + deterministic dedup by `record.id` |

**Multi-scope retrieval**:

```typescript
// Case C: Multiple scopes — retrieve per-scope, merge + dedup
const results = await Promise.all(
  allowedScopes.map((scope) =>
    deps.memoryRetriever.retrieve({ ownerId, projectId, topicId, scope })
  )
);
records = deduplicateMemoryRecords(results.flat());
```

**Invariants**:
- Every retrieval call carries `ownerId`, `projectId`, `topicId` (never lost)
- Deduplication: `record.id` as unique key, first-occurrence-wins
- Order is deterministic (preserved from retrieval order)
- Runtime does NOT redefine Memory Scope semantics — only executes Runtime Policy

### 15.7 P0.7.2 Unified Retrieval Architecture

P0.7.2 extends Runtime with a **unified multi-source context retrieval** pipeline:

```
                     Runtime Request
                            ↓
                  Runtime Context Policy
                            ↓
                    Context Retrieval
                            │
           �────────────────┼────────────────┐
           ↓                ↓                ↓
        Memory           Decision          Outcome
           ↓                ↓                ↓
        Context          Context           Context
           │                │                │
           ├─────────────── Feedback ────────�
           │
           ├──────── Knowledge
           │
           └──────── Graph Enrichment
                            ↓
                Scope / Owner Validation
                            ↓
                 Deterministic Dedup
                            ↓
                 ContextObject[]
```

**Key Design Principles**:

1. **Single Entry Point**: `retrieveRuntimeContextWithMetadata()` is the unified retrieval API
2. **Source Isolation**: Each source (memory, decision, outcome, feedback, knowledge, graph) has dedicated retrieval function
3. **No Cross-Contamination**: Decision/Outcome records are excluded from general memory branch
4. **Scope Validation**: All contexts undergo owner/project/topic boundary validation
5. **Kind Filters**: `allowedKinds`/`excludedKinds` applied uniformly across all sources
6. **Deterministic Dedup**: By `context.id`, first-occurrence-wins
7. **Diagnostics**: Per-source status reporting (included/disabled/unavailable/failed)

### 15.11 Scope & Boundary Hardening (P0.7.2-R1)

**Owner Isolation Strengthening**:

`validateContextScope()` now enforces strict owner isolation across all sources:

1. **Owner Match**: If `provenance.ownerId` is present, it MUST equal `request.ownerId`. No exceptions.
2. **No-Owner Policy**: Unowned data (no `ownerId`) is REJECTED unless it is legitimate shared knowledge:
   - `sourceType === 'knowledge'` AND
   - `scope === 'global'` AND
   - No `projectId` or `topicId` restrictions
3. **Unknown Scope**: Contexts with `scope === 'unknown'` are always rejected (no default-allow).
4. **Scope Policy**: When `allowedScopes` is non-empty, context scope MUST be in the allowed list.

**Error Propagation Policy**:

| Source | Failure Mode | Behavior |
|--------|-------------|----------|
| Memory (primary) | Any error | **Throw** `ContextOSRuntimeError` (RUNTIME_EXECUTION) |
| Decision | Any error | Mark source as `failed`, continue |
| Outcome | Any error | Mark source as `failed`, continue |
| Feedback | Any error | Mark source as `failed`, continue |
| Knowledge | Any error | Mark source as `failed`, continue |
| Graph | Any error | Mark source as `failed`, continue |

**Source Status Semantics**:

| Status | Meaning |
|--------|---------|
| `included` | Source executed successfully, returned >= 0 contexts |
| `disabled` | Policy explicitly turned off this source (`include*: false`) |
| `unavailable` | Required optional provider not configured |
| `failed` | Source execution threw an error |

**Outcome Metadata Preservation**:

Outcome retrieval results include scanning metadata in `RuntimeContextSourceReport.metadata`:

```typescript
interface RuntimeContextSourceMetadata {
  scannedRecords: number;   // Total records scanned across batches
  batchesFetched: number;   // Number of batch fetches performed
  truncated: boolean;       // True if retrieval was bounded before exhaustion
  exhausted: boolean;       // True if all matching records were retrieved
}
```

Multi-scope outcome retrieval aggregates metadata conservatively: `truncated = any truncated`, `scannedRecords = sum`, `exhausted = all exhausted`.

**Scope Threading (P0.7.2-R1)**:

All domain-specific retrieval paths (Decision, Outcome, Feedback) now accept `scope` parameter:

```typescript
// DecisionRetrievalParams
scope?: MemoryScope;  // 'global' | 'project' | 'topic'

// OutcomeRetrievalParams  
scope?: MemoryScope;
```

The Runtime passes `allowedScopes[0]` when single-scope, or iterates per-scope with dedup for multi-scope.

### 15.12 Final Scope Completeness & Acceptance (P0.7.2-R3)

**Scope Missing Vulnerability Fix**:

Prior to R3, `validateContextScope()` had a gap: when `allowedScopes` was non-empty but a context's `provenance.scope` was `undefined`/`null`, the scope check was silently skipped, allowing context without scope metadata to bypass the allowedScopes restriction.

R3 fixes this with strict enforcement:

1. **Scope Presence**: When `allowedScopes` is non-empty, `provenance.scope` MUST exist, be a valid scope (`global`/`project`/`topic`), AND belong to the allowed list. Missing scope → REJECT.
2. **Scope-Specific Provenance Integrity** (always enforced when scope is present):
   - `scope === 'global'`: must NOT carry `projectId` or `topicId` (contradicts global boundary).
   - `scope === 'project'`: must have valid `projectId`, must NOT carry `topicId`.
   - `scope === 'topic'`: must have both valid `projectId` AND `topicId`.
3. **Contradiction Guard**: Even when `allowedScopes` is empty, scope/project/topic contradictions are rejected (e.g., `scope='global'` + `projectId` present → REJECT).
4. **MemoryScope vs ContextScope**: `MemoryScope` includes `'session'` but `ContextScope` does not. Session-scoped memory data is rejected by validateContextScope since `'session'` is not a recognized ContextScope value.

## 21. P0.7.4 — Agent Run Memory & Persistence

### 21.1 Overview

P0.7.4 upgrades `ContextOSRun` from a transient in-memory object to a persisted database record. The Run lifecycle (started → completed/failed) is now stored durably, enabling Run history, status tracking, and auditability.

### 21.2 Design Principles

1. **Owner isolation** — Every query MUST carry `ownerId`; cross-owner data leaks are treated as security failures
2. **Backward compatibility** — All new `AgentRun` fields are NULLABLE; existing records remain valid
3. **Dependency injection** — `runStore` is optional; Runtime works in-memory when no store is configured
4. **Deterministic IDs** — Run IDs follow `run_${ownerId}_${timestamp}` (no UUID/random)
5. **Explicit error semantics** — `RunConflictError`, `RunNotFoundError`, `RunPersistenceError` are distinct

### 21.3 Architecture Diagram

```
ContextOSRuntimeRequest
        ↓
runContextOS()
        ↓
   Create Run (in memory)
        ↓
   [runStore.create(run)] ← Persist "started"     (P0.7.4 NEW)
        ↓
   Retrieve Context
        ↓
   Assemble Context
        ↓
   [runStore.update(completedRun)] ← Persist "completed" (P0.7.4 NEW)
        ↓
   Return result

   On error:
   [runStore.update(failedRun)] ← Persist "failed"    (P0.7.4 NEW)
        ↓
   Throw ContextOSRuntimeError
```

### 21.4 New Modules

| Module | Path | Responsibility |
|--------|------|----------------|
| Run Store Contract | `src/runtime/run-store.ts` | `ContextOSRunStore` interface, error types, query/pagination types |
| Prisma Adapter | `src/runtime/prisma-run-store.ts` | `PrismaContextOSRunStore` — AgentRun persistence with owner isolation |

### 21.5 Schema Extension (Compatible)

| Column | Type | Purpose |

### 21.6 Error Types

| Error | Code | When |
|-------|------|------|
| `RunConflictError` | `RUNTIME_EXECUTION` | Duplicate ID on create |
| `RunNotFoundError` | `RUNTIME_NOT_FOUND` | Get/update with wrong owner or non-existent ID |
| `RunPersistenceError` | `RUNTIME_EXECUTION` | Unexpected storage-layer failure |

### 21.7 Pagination Strategy

Composite cursor pagination on `(createdAt, id)` for deterministic ordering:

- Cursor format: `base64(JSON({ createdAt: string, id: string }))`
- Query: `WHERE ownerId = ? AND (createdAt > cursor OR (createdAt = cursor AND id > cursor))`
- Order: `createdAt ASC, id ASC`
- Default limit: 20, max: 100
- `totalCount: -1` (omitted for performance; requires separate COUNT query)

### 21.8 Lifecycle Persistence Semantics

| Phase | Store Operation | Status |
|-------|----------------|--------|
| Pre-retrieval | `create(run)` | `started` |
| Post-assembly | `update(completedRun)` | `completed` |
| On error | `update(failedRun)` | `failed` |

When `runStore` is NOT configured: all persistence is skipped (pure P0.7.1 — P0.7.3 behavior preserved).

### 21.10 P0.7.4-R1 Hardening

P0.7.4-R1 addresses boundary issues identified in code review:

#### Limit Validation Policy

| Input | Behavior |
|-------|----------|
| `undefined` / omitted | Uses `DEFAULT_RUN_LIMIT` (20) |
| Positive integer ≤ MAX | Used as-is |
| Positive integer > MAX | Clamped to `MAX_RUN_LIMIT` (100) |
| `0` | Throws `RunValidationError` ("must be a positive integer") |
| Negative (`-1`, `-100`) | Throws `RunValidationError` ("must be a positive integer") |
| Fractional (`1.5`, `3.7`) | Throws `RunValidationError` ("must be an integer") |
| `NaN` | Throws `RunValidationError` ("must be a finite number") |
| `Infinity` / `-Infinity` | Throws `RunValidationError` ("must be a finite number") |

#### Cursor Validation Behavior

A supplied cursor MUST:
- Be a non-empty string (whitespace-only rejected, empty string explicitly rejected)
- Be canonical Base64: valid alphabet (`A-Za-z0-9+/=`), correct padding (length multiple of 4), and decode→re-encode produces the same string (guards against Node's permissive `Buffer.from` silently ignoring invalid characters)
- Decode from base64 to valid JSON
- Be a JSON object (arrays/primitives/null rejected)
- Contain a valid ISO 8601 timestamp in `createdAt` matching `Date.toISOString()` format (`YYYY-MM-DDTHH:mm:ss.sssZ`)
- Contain a non-empty, non-whitespace string in `id`

Any violation throws `RunValidationError`. Malformed cursors never silently restart pagination.

#### Empty Cursor Regression (R1.1)

**Bug**: `query.cursor ? parseCursor(query.cursor) : null` treated an explicit empty string `""` as if cursor was omitted, silently restarting pagination from page 1.

**Fix**: Changed to `query.cursor !== undefined ? parseCursor(query.cursor) : null`. Now:
- `cursor === undefined` (omitted) → first page
- `cursor === ""` (empty string) → throws `RunValidationError`
- `cursor === "   "` (whitespace) → throws `RunValidationError`
- Valid cursor → proceeds normally
- Invalid cursor → throws, never falls back to first page

#### Owner ID Validation on Create (R1.1)

**Bug**: `create()` did not validate `run.ownerId`, allowing empty/blank owner IDs to reach the database.

**Fix**: Added `validateOwnerId(run.ownerId)` call BEFORE `getPrisma()` acquisition in `create()`. Now:
- Empty string ownerId → throws `RunValidationError` (not `RunPersistenceError`)
- Whitespace-only ownerId → throws `RunValidationError`
- Invalid ownerId → never writes any database row
- Valid ownerId + duplicate ID → still throws `RunConflictError` (preserved)

#### Owner-Scoped Read and Update Guarantees

- `getById()`: Uses `findFirst({ where: { id, ownerId } })` for atomic scoped lookup. Returns `null` for unknown runs AND cross-owner access — same response either way.
- `update()`: Uses `updateMany({ where: { id, ownerId } })` for atomic owner-scoped update. If count === 0, throws `RunNotFoundError`. Then reads back via scoped `findFirst`.
- `list()`: Validates `ownerId` is non-empty before DB access. Owner filter always present in WHERE clause.

### 21.12 P0.7.4-R1.2 Preflight Validation & Canonical Date Checks

#### Problem

The `update()`, `getById()`, and `list()` methods acquired the Prisma client (`await getPrisma()`) **before** validating inputs. While `create()` validated ownerId first, the other three would establish a database connection before checking whether the request was even valid.

Additionally, `parseCursor()` checked timestamp shape (ISO regex) and that `new Date(iso).getTime()` was not NaN. However, JavaScript silently **normalizes** impossible calendar dates: `2026-02-30` → `2026-03-02`, `2026-13-01` → `2027-01-01`. These pass both the regex and the `!isNaN()` check while representing a different date than the input.

#### Fixes Applied

1. **Preflight ordering**: `update()`, `getById()`, and `list()` now validate ALL inputs **before** `await getPrisma()`. No invalid request acquires a Prisma client or executes a database query.
2. **Canonical date identity**: `parseCursor()` now requires `date.toISOString() === obj.createdAt`. This catches any silent normalization because `new Date('2026-02-30').toISOString()` returns `'2026-03-02T00:00:00.000Z'` — which does NOT match the input `'2026-02-30T00:00:00.000Z'`.
3. **Finite check**: `isNaN(date.getTime())` replaced with `!Number.isFinite(date.getTime())` for stricter edge-case coverage.

## 22. P0.7.5 — Runtime Learning Pipeline

### 22.1 Overview

P0.7.5 implements the Runtime Learning Pipeline: **LearningCandidate → Policy → MemoryStore**. The pipeline transforms runtime signals (decision + feedback) into durable memory records after passing a deterministic policy-evaluation gate.

**Module**: `src/runtime/runtime-learning.ts`
**Public API** (barrel export from `src/runtime/index.ts`):
- `runRuntimeLearning(input, deps)` — Full orchestrator (async)
- `evaluateLearningCandidate(candidate, policy)` — Pure policy evaluator
- `validatePolicy(partial?)` — Policy construction with full validation
- `DEFAULT_LEARNING_POLICY` — Immutable default policy object

### 22.2 Architecture Diagram

```
buildLearningCandidates()  [P0.6.7 Context Loop — reused]
       ↓
  LearningCandidate[]
       ↓
runRuntimeLearning()
  ├── Phase 1: Authorization Preflight (fail-closed)
  │     validateAuthenticatedOwner()
  │     preflightSources()         — decision/feedback owner check
  │     preflightCandidates()      — generated candidate owner check
  ├── Phase 2: Policy validation  — validatePolicy()
  ├── Phase 3: Timestamp injection — injected clock (deterministic)
  ├── Phase 4: Generate candidates — buildLearningCandidates()
  ├── Phase 5: Capacity control   — maxCandidatesPerRun slice
  ├── Phase 6: Evaluate + persist (per candidate)
  │     ├── evaluateLearningCandidate()  → eligible | discarded
  │     └── persistEligibleCandidate()   → persisted | already_exists | failed
  └── Phase 7: Aggregate counters  — buildResult()
       ↓
  RuntimeLearningResult
```

### 22.3 Design Principles

1. **Three-phase processing** — generate → evaluate → persist
2. **Deterministic policy evaluation** — `evaluateLearningCandidate()` has no side effects
3. **Owner isolation** — enforced at batch preflight AND per-record persistence
4. **Idempotent persistence** — owner-scoped `getById` before `create`
5. **Fail-closed** — any auth/owner mismatch throws before any storage I/O
6. **Deduplicated IDs** — `mem_${candidateId}` (deterministic, no UUID)
7. **Per-candidate error isolation** — one persistence failure does not crash the entire run

### 22.4 Default Policy

| Setting | Value | Rationale |
|---------|-------|-----------|
| `minConfidence` | 0.3 | Filter low-confidence candidates |
| `minImportance` | 0 | No threshold by default |
| `maxCandidatesPerRun` | 20 | Capacity control per execution |
| `allowedCandidateTypes` | `['decision_pattern', 'successful_pattern', 'failure_pattern', 'preference_signal', 'strategy_signal']` | Known candidate types |
| `allowedScopes` | `['topic', 'project']` | **Global scope prohibited by default** |
| `requireOutcomeEvidence` | `true` | Outcome linkage required |

The default policy uses `Object.freeze()` on nested arrays to prevent accidental mutation of shared state.

### 22.5 Scope Resolution

Candidates are assigned a memory scope based on their context linkage:

| Candidate has | Resolved scope | Memory keys |
|---------------|---------------|-------------|
| `topicId` | `topic` | `topicId` + `projectId` |
| `projectId` only | `project` | `projectId` |
| Neither | `global` | none |

Scope allowlist policy: candidates resolving to a scope not in `policy.allowedScopes` are discarded with `SCOPE_NOT_ALLOWED`.

### 22.6 Owner Isolation and Fail-Closed Preflight

**Preflight (Phase 1)** — Executes before any storage I/O:
1. `authenticatedOwnerId` must be a non-empty string
2. Every `source.decision.ownerId` must equal `authenticatedOwnerId`
3. Every `source.feedback.ownerId` must equal `authenticatedOwnerId`
4. Every `feedback.decisionId` must match its paired `decision.id`
5. All generated `LearningCandidate.ownerId` must equal `authenticatedOwnerId`

**Fail-closed**: any mismatch throws `LearningAuthorizationError` before any `getById` or `create` call. Verified by tests 3.x which confirm zero storage operations on rejection (mock `getById` and `create` call counts == 0).

### 22.7 Idempotency and Duplicate-Key Race Behavior

```typescript
// persistEligibleCandidate() — pseudo-code:
try {
  existing = getById(memId, ownerId)    // Step 1: owner-scoped read
  if (existing) return already_exists
} catch {
  return failed { errorCode: 'PERSISTENCE_READ_FAILED' }
}

try {
  create(record)                        // Step 2: write
  return persisted
} catch (MemoryConcurrencyError) {
  try {
    raced = getById(memId, ownerId)     // Step 3: owner-scoped recheck
    if (raced) return already_exists    // owned → true duplicate
    return failed { errorCode: 'DUPLICATE_ID_CONFLICT' }  // foreign owner
  } catch {
    return failed { errorCode: 'DUPLICATE_RECHECK_FAILED' }  // cannot confirm
  }
} catch {
  return failed { errorCode: 'PERSISTENCE_WRITE_FAILED' }   // generic write error
}
```

**Key guarantees**:
- Foreign-owner collisions return `DUPLICATE_ID_CONFLICT` — never `already_exists`
- A recheck failure returns `DUPLICATE_RECHECK_FAILED` — never `already_exists` (unconfirmed ≠ owned)
- Raw database error messages are never exposed to the caller
- `create()` failures that are not `MemoryConcurrencyError` return `PERSISTENCE_WRITE_FAILED`

### 22.8 Error Codes (errorCode)

Distinct from `reasonCode` (which carries policy-evaluation semantics), `errorCode` carries operational failure semantics:

| Error Code | Condition |
|------------|-----------|
| `PERSISTENCE_READ_FAILED` | Initial `getById()` threw |
| `PERSISTENCE_WRITE_FAILED` | `create()` threw a non-concurrency error |
| `DUPLICATE_ID_CONFLICT` | `MemoryConcurrencyError` + owner-scoped recheck returned null (foreign-owner record) |
| `DUPLICATE_RECHECK_FAILED` | `MemoryConcurrencyError` + owner-scoped recheck itself threw |

A failed result is **never** represented as policy evaluation failure (`reasonCode` carries only policy semantics).
A failed result is **never** represented as persisted or `already_exists`.
A persisted result never carries an `errorCode`.

### 22.9 Aggregate Counters

`buildResult()` recomputes all counters from the returned item list:

```typescript
{
  items: RuntimeLearningItemResult[],  // per-candidate results
  counts: {
    persisted: number,       // status === 'persisted'
    discarded: number,       // status === 'discarded' (policy reject or over limit)
    already_exists: number,  // status === 'already_exists' (idempotent skip)
    failed: number,          // status === 'failed' (persistence error)
    total: number,           // items.length (sum of above)
  },
  processingTimestamp: string,  // ISO-8601 injected clock
}
```

Counters always match the item list — verified under both success and failure conditions (tests 5.1, 5.7, 6.7).

## 24. P0.7.6 — End-to-End Agent Context Loop

### 24.1 Overview

P0.7.6 is the **composite orchestration** that wires P0.7.1–P0.7.5 subsystems into a single durable execution path — from request validation through context retrieval/assembly, Agent execution, learning evidence resolution, and P0.7.5 memory persistence.

Unlike `runContextOS()` (P0.7.1), which marks the Run `completed` immediately after assembly, `runContextOSAgentLoop()` introduces a `running` state and executes the Agent BEFORE the Run is marked `completed`. This creates a recoverable mid-execution state: a crash during Agent execution leaves the Run in `running` status (recov
erable) rather than silently lost.

### 24.2 Architecture Position

```
  User / Application
       │
       ▼
  runContextOSAgentLoop()         ← NEW (P0.7.6 Composite)
       │
       ├── validate request
       ├── create Run (started)    ← P0.7.1 createStartedRun
       ├── persist Run (started)   ← P0.7.4 ContextOSRunStore.create
       ├── retrieve contexts       ← P0.7.2 retrieveRuntimeContext
       ├── assemble contexts       ← P0.7.3 assembleRuntimeContext
       ├── persist Run (running)   ← P0.7.6 NEW status
       ├── execute Agent           ← P0.7.6 injected executor
       ├── resolve learning ev.   ← P0.7.6 injected resolver
       ├── P0.7.5 learning        ← P0.7.5 runRuntimeLearning
       ├── persist Run (completed) ← P0.7.4 ContextOSRunStore.update
       └── return result
```

### 24.3 Key Design Decisions

1. **Orchestration only** — No domain logic. No provider coupling.
2. **Business-agnostic** — No hardcoding of Douyin/content/viral.
3. **Deterministic** — Injected clock, collision-resistant IDs (contentHash + taskId), no randomness.
4. **Owner isolation** — Enforced at every stage.
5. **Three injected contracts** — Agent executor, Learning evidence resolver, Clock.
6. **Learning ≠ Run failure** — Learning pipeline failure doesn't mark the Run as failed.
7. **Defensive ID sanitization** — Agent-returned IDs are deduped and validated.
8. **Fail-closed auth** — Owner mismatch in learning sources throws before storage I/O.

### 24.4 The `running` State

The `ContextOSRun.status` now supports three lifecycle statuses:

```
started → running → completed
                 ↘ failed
```

- **`started`**: Run record created, not yet persisted as `running`.
- **`running`**: Contexts assembled; Agent about to execute (or executing). This stage is persisted BEFORE Agent execution so that a crash mid-execution leaves a recoverable state.
- **`completed`**: Agent finished; final state persisted with output + IDs.
- **`failed`**: Any stage of retrieval/assembly/Agent execution threw. Learning failures do NOT cause `failed` status.

### 24.5 Learning Stage Outcome

The `RuntimeAgentLearningStageOutcome` type distinguishes four terminal states (R1 clarified):

| Outcome | Meaning | Diagnostic Key | runStore Impact |
|---------|---------|----------------|------------------|
| `completed` | Pipeline executed AND zero `counts.failed` | `diagnostics.learning = 'completed'` | Run marked `completed` |
| `no_evidence` | Resolver returned `[]` — no candidates to evaluate | `diagnostics.learning = 'skipped'` | Run marked `completed` |
| `skipped` | No `memoryStore` — learning never attempted | `diagnostics.learning = 'skipped'` | Run marked `completed` |
| `failed` | Pipeline threw, or `counts.failed > 0`, or resolver threw | `diagnostics.learning = 'failed'` | Run marked `completed` |

**Critical R1 invariant — Agent 成功 ≠ Learning 成功；没有证据 ≠ 证据解析没有出错**:
- Pipeline **执行完成**（函数返回）≠ **所有候选都持久化成功**（`counts.failed === 0`）
- `no_evidence`（resolver 正常返回空数组）≠ `failed`（resolver 抛出异常）
- **Learning failure is NEVER a Run failure.** The Agent succeeded even if learning didn't.

### 24.5.1 Run ID Uniqueness (R1)

Run ID 格式: `run_{ownerId}_{taskId?}_{contentHash}_{timestamp}`

- `taskId`（可选）是追踪标识，不是幂等键。不同请求使用同一 taskId 会产生不同 Run。
- `contentHash` 是 `{purpose, input}` 的确定性哈希，确保不同请求即使在同一时间戳下也不会冲突。
- 两个相同 (owner, taskId, purpose, input, timestamp) 的请求产生相同 ID（合法重试）。
- 与 `runContextOS()` 的 `createRuntimeRunId()` 行为独立，不破坏既有行为。

### 24.8 ID Sanitization (`sanitizeIdArray`)

Agent-returned ID arrays pass through defensive sanitization:
- Deduplicated (first-occurrence order preserved)
- Non-string values filtered out
- Empty/whitespace-only values filtered out
- Returns a new array (does not mutate input)
- Non-array input → `[]`

This prevents malformed Agent output from propagating into learning pipeline or Run record fields.

### 24.9 Error Recovery

When retrieval/assembly/Agent execution fails:
1. The Run is persisted with `status: 'failed'`.
2. Partial execution context (contextIds, output, decision/outcome IDs) is preserved where available.
3. If the failed-state persistence also throws, both errors are surfaced without losing the original.

Learning pipeline failures are caught separately and reported in `diagnostics.warnings` — the Run is still marked `completed`.
