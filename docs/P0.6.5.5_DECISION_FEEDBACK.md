> On-demand feedback synthesis from Decision → attributed Outcomes.

**Status**: Completed 2026-10-03

## 1. Overview

P0.6.5.5 implements the **Decision Feedback Layer** — the bridge between Decision Memory and Outcome Memory. It provides deterministic, on-demand synthesis of feedback: given a Decision and all Outcomes attributed to it, produce a structured **DecisionFeedback** object that summarizes evidence, aggregates metrics, and highlights trends.

### Core Principle

```
DecisionMemory  +  OutcomeMemory[]  +  OutcomeRetrievalMetadata
       ↓
DecisionFeedbackServiceImpl.buildFeedback()
       ↓
DecisionFeedback (derived, NOT persisted)
```

### Design Tenets

| # | Principle |
|---|-----------|
| 1 | Decision-Outcome relationship = **SOLELY** via `payload.attribution.decisionId` |
| 2 | All feedback is **ON-DEMAND** — no persistence of derived results |
| 3 | **No LLM** — purely deterministic computation |
| 4 | **No DB writes** — feedback never persisted back to database |
| 5 | **Defense-in-depth isolation** — Owner/Project/Topic re-verified at Service layer |
| 6 | Reuses `OutcomeAggregationService` for metric aggregation and trend analysis |
| 7 | Completeness is **HONEST** — propagates retrieval truncation via metadata |
| 8 | No causal inference — observations only, no judgment |
| 9 | Stateless service — safe as singleton |

## 3. Core Types

### 3.1 DecisionFeedback

The primary output type — a complete summary of evidence for a Decision:

| Field | Type | Description |
|-------|------|-------------|
| `id` | `string` | Stable derived-view identifier (`dfb_{decisionId}`) |
| `ownerId` | `string` | Owner (user) ID — inherited from Decision |
| `decisionId` | `string` | The Decision this feedback is for |
| `decisionStatus` | `DecisionStatus` | Current status of the Decision (`proposed`/`active`/`superseded`/`reversed`) |
| `decisionCreatedAt` | `string` | ISO timestamp of Decision creation |
| `expectedOutcome` | `string \| undefined` | Expected outcome statement (preserved, not interpreted) |
| `outcomeCount` | `number` | Number of attributed+isolated Outcomes |
| `outcomeIds` | `string[]` | Outcome IDs in observedAt ASC order |
| `outcomeTypes` | `OutcomeType[]` | Unique outcome types (first-seen order) |
| `firstObservedAt` | `string \| undefined` | Earliest observation timestamp |
| `lastObservedAt` | `string \| undefined` | Latest observation timestamp |
| `metricAggregations` | `OutcomeMetricAggregation[]` | Per-metric statistics (reused from Aggregation) |
| `trends` | `OutcomeMetricTrend[]` | Adjacent-window trend comparison |
| `status` | `DecisionFeedbackStatus` | Computed feedback status |
| `completeness` | `'complete' \| 'bounded'` | Honest completeness indicator |
| `generatedAt` | `string` | ISO timestamp of computation |

### 3.2 DecisionFeedbackStatus

```typescript
type DecisionFeedbackStatus =
  | 'no_evidence'          // Retrieval completed, zero attributed outcomes found
  | 'evidence_available'   // One or more attributed outcomes found, complete retrieval
  | 'bounded';             // Retrieval truncated, outcomes exist but may be incomplete
```

Status determination logic:

| Condition | Status |
|-----------|--------|
| `outcomeCount === 0` AND `completeness === 'complete'` | `no_evidence` |
| `outcomeCount > 0` AND `completeness === 'complete'` | `evidence_available` |
| `completeness === 'bounded'` (regardless of count) | `bounded` |

## 4. Pure Functions

### 4.1 Attribution Matching

```typescript
function isOutcomeAttributedToDecision(
  outcome: OutcomeMemory,
  decisionId: string
): boolean
```

**Rule**: Returns `true` ONLY when `outcome.payload.attribution?.decisionId === decisionId`. No implicit matching, no fuzzy logic, no fallback.

### 4.2 Completeness Determination

```typescript
function determineDecisionFeedbackCompleteness(
  retrievalMetadata: OutcomeRetrievalMetadata
): 'complete' | 'bounded'
```

**Rule**: Directly propagates `retrievalMetadata.truncated` — `true` → `'bounded'`, `false` → `'complete'`. Honest reflection of retrieval coverage.

### 4.3 Status Determination

```typescript
function determineDecisionFeedbackStatus(
  outcomeCount: number,
  completeness: 'complete' | 'bounded'
): DecisionFeedbackStatus
```

**Rule**: Stateless pure function of outcome count and completeness. `bounded` completeness always produces `bounded` status regardless of count.

### 4.4 Attribution Confidence (Extended)

```typescript
function computeAttributionConfidence(
  outcome: OutcomeMemory,
  decisionId: string
): 'explicit' | 'none'
```

Returns `'explicit'` when `attribution.decisionId` matches, `'none'` otherwise. Designed for future multi-source attribution — currently binary.

## 5. Service Layer

### 5.1 DecisionFeedbackService Interface

```typescript
interface DecisionFeedbackService {
  buildFeedback(
    decision: DecisionMemory,
    outcomes: OutcomeMemory[],
    retrievalMetadata: OutcomeRetrievalMetadata,
  ): DecisionFeedback;
}
```

### 5.2 Processing Pipeline

The `buildFeedback()` method executes 10 sequential steps:

1. **filterAndIsolateOutcomes** — Attribution + Defense-in-Depth isolation
2. **Sort** — by `observedAt` ASC
3. **Collect IDs** — outcome ID list
4. **Collect Types** — unique outcome types (first-seen order)
5. **First/Last observedAt** — boundary timestamps
6. **Aggregate Metrics** — delegates to `OutcomeAggregationService.aggregate()`
7. **Calculate Trends** — delegates to `OutcomeAggregationService.compareWindows()`
8. **Determine Completeness** — from retrieval metadata
9. **Determine Status** — from outcome count + completeness + decision status
10. **Construct** — assemble DecisionFeedback object

### 5.3 Isolation Rules (Defense-in-Depth)

| Check | Rule | Rationale |
|-------|------|----------|
| Owner | `outcome.ownerId === decision.ownerId` | Prevents cross-user data leakage |
| Project | If `decision.projectId != null`: `outcome.projectId === decision.projectId` | Scoped decision, scoped outcomes |
| Topic | If `decision.topicId != null`: `outcome.topicId === decision.topicId` | Scoped decision, scoped outcomes |
| Attribution | `outcome.payload.attribution?.decisionId === decision.id` | Explicit link only |

These checks are **redundant** with retrieval-level isolation but provide defense-in-depth against programming errors in retriever implementations.

### 5.4 Time Window Handling

**Feedback Time Window**: Uses `[windowStart, windowEnd)` (half-open interval).

- `observedAt >= windowStart` and `observedAt < windowEnd`
- Resolved by `resolveDecisionFeedbackWindow(decisionCreatedAt, options)`
- Default: `[decisionCreatedAt, now]` (full lifetime of the decision)
- Can be narrowed via explicit `windowStart`/`windowEnd` parameters
- Validation: `windowStart` MUST be strictly less than `windowEnd`

**Aggregation & Trend Window**: Uses the same `[windowStart, windowEnd)` feedback window.

- Both aggregation and trend computation use the feedback window for filtering.
- Previous trend window is automatically derived as equal-length preceding window.
- If `windowEnd <= windowStart`, aggregation/trend is skipped gracefully.

## 7. Design Decisions

### 7.1 Why On-Demand?

Feedback is a **derived view** of immutable Outcome facts. Persisting it would:
- Introduce write amplification
- Require invalidation logic on every new Outcome
- Add complexity without benefit

On-demand ensures feedback is always fresh and consistent with the latest data.

### 7.2 Why No LLM?

Feedback synthesis is **objective** — counting, statistics, and trend comparison. LLM involvement would:
- Introduce non-determinism
- Add latency and cost
- Risk hallucinated "insights"

All computation is pure-function deterministic.

### 7.3 Why Reuse OutcomeAggregationService?

The metrics and trend computations are identical. Reusing:
- Avoids code duplication
- Ensures consistent numeric semantics
- Reduces maintenance surface

### 7.4 Why Defense-in-Depth Isolation?

Even if the retriever correctly filters by owner/project/topic, the service re-verifies. This guards against:
- Future retriever bugs
- Direct service callers passing unfiltered data
- Schema evolution breaking retriever assumptions

### 7.5 Why Half-Open Window `[start, end)`?

The feedback window uses standard half-open interval semantics: `observedAt >= windowStart` and `observedAt < windowEnd`. This is consistent across retrieval, aggregation, and trend computation. The window is resolved once at the entry point and threaded through the entire pipeline via `DecisionFeedbackBuildOptions`.

## 9. Non-Goals

| Excluded | Rationale |
|----------|----------|
| Persisting Feedback | Feedback is derivable — on-demand is sufficient |
| Causal Inference | Correlation ≠ causation — we report observations only |
| LLM Judgment | Adding interpretation would introduce non-determinism |
| Automatic Decision Modification | Feedback informs humans; it doesn't act |
| Cross-Decision Analysis | Each feedback is scoped to a single Decision |
| Alert Integration | Alerts are orthogonal (P0.6.5.3); feedback is passive summary |

## 12. P0.6.5.5-R1 — Hardening (2026-10-03)

### 12.1 What Changed

R1 hardening addresses three gaps in the original P0.6.5.5 release:

1. **Time Window Consolidation** — `windowStart`/`windowEnd` now flow consistently from Entry Point → Retrieval → Aggregation → Trend, eliminating the previous split where observation range and decision-time range were used concurrently.
2. **Context Bridge** — `decision-feedback-bridge.ts` converts `DecisionFeedback` → `ContextObject<DecisionFeedbackContextPayload>` for consumption by Context Assembly.
3. **Stable Feedback ID** — `dfb_${decisionId}` (deterministic, no timestamp) replaces the previous `dfb_${decisionId}_${timestamp}` pattern.
4. **Decision Retrieval** — `getDecisionById()` in `decision-memory-retrieval.ts` provides exact-id lookup via `MemoryRetriever.retrieve({ id, ownerId })`, producing an O(1) database query: `WHERE ownerId = ? AND id = ?`.

### 12.3 DecisionFeedbackBuildOptions

```typescript
interface DecisionFeedbackBuildOptions {
  windowStart: string;   // Resolved at Entry Point
  windowEnd: string;     // Resolved at Entry Point
  requestNow: string;    // Generated once at Entry Point (ISO 8601)
}
```

This ensures the same `requestNow` is used for `generatedAt`, aggregation, and trend computation within a single feedback cycle.

### 12.4 resolveDecisionFeedbackWindow()

Resolves the authoritative time window for feedback computation:

| Input | Output |
|-------|--------|
| No explicit params | `[decisionCreatedAt, now]` |
| Only `windowStart` | `[provided, now]` |
| Only `windowEnd` | `[decisionCreatedAt, provided]` |
| Both provided | `[provided, provided]` |

Validation: `windowStart` MUST be strictly less than `windowEnd` (throws `Error` otherwise). Invalid ISO dates also throw.

### 12.5 Context Bridge Design

The bridge converts a `DecisionFeedback` into a `ContextObject` with:

| Field | Value |
|-------|-------|
| `kind` | `'decision'` (consistent with decision contexts) |
| `type` | `'decision_feedback'` (clearly marks as DERIVED, not raw decision) |
| `confidence` | From `feedbackConfidence(status, completeness)` |
| `provenance.source` | `decision_feedback:${decisionId}` |
| `provenance.sourceType` | `'decision_feedback'` |

**Confidence mapping**: 0.9 (evidence+complete), 0.7 (no evidence+complete), 0.6 (bounded), 0.4 (no evidence+bounded).

### 13.2 Exact-ID Retrieval Pipeline

```
buildDecisionFeedback()
      ↓

      ↓

```

### 13.4 MemoryRetrievalRequest.id Semantics

- **Always combined with ownerId** — id-only queries are never permitted.
- **Structural criterion** (like projectId/topicId), NOT a policy.
- **O(1) database lookup** via `WHERE ownerId = ? AND id = ?` (primary key).
- **Paired with policy filters**: scope, status, type all apply simultaneously.

### 13.5 Owner Isolation at Query Layer

```
{ ownerId: 'user-A', id: 'decision-owned-by-user-B' }
    ↓
WHERE id = 'decision-owned-by-user-B' AND ownerId = 'user-A'
    ↓
return null (no match at DB level)
```

Existence is never leaked across owner boundaries.

### 13.6 Decision Status Support

`getDecisionById()` includes ALL decision statuses:

- `proposed` → Memory DB status `active` (via `decisionStatusToMemoryStatus`)
- `active` → Memory DB status `active`
- `superseded` → Memory DB status `superseded` (includeSuperseded: true)
- `reversed` → Memory DB status `archived` (includeArchived: true)

Policy: `includeSuperseded: true`, `includeArchived: true`, `maxResults: 1`.
