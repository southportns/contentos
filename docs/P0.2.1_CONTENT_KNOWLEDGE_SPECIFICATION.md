# P0.2.1 — Content Knowledge Specification

> **Version**: 1.0  
> **Date**: 2026-09-02  
> **Task Type**: Architecture Specification  
> **Status**: PASS  
> **Scope**: Define what "Content Knowledge" means in ContextOS and how it should be stored, validated, updated, and retrieved

---

## 1. Executive Summary

**What was designed**: A comprehensive Content Knowledge specification for ContextOS, defining the conceptual model, taxonomy, lifecycle, evidence system, versioning, relations, and retrieval architecture.

**What was intentionally NOT implemented**: No database changes, no new Prisma Schema, no migrations, no Vector DB, no RAG, no fine-tuning. This is purely a design specification for P0.2.2 implementation.

---

## 2. P0.2 Objective

P0.1 answered: **"How does ContextOS write more like a human?"**  
P0.2 answers: **"How does ContextOS preserve what it learns and actually use it later?"**

The goal of P0.2.1 is to define the **target state**: what a Content Knowledge System should look like in ContextOS, so that P0.2.2+ can implement it correctly.

## 3. Concept Definitions

### 3.1 The Five Core Concepts

| Concept | Definition | Example | Nature |
|---------|-----------|---------|--------|
| **Raw Content** | Original material collected by ContextOS | Douyin video, transcript, title, comments, likes | Data |
| **Observation** | Phenomenon noticed in raw content | "This content uses many oral connectors" | Insight |
| **Knowledge Pattern** | Reusable rule validated across multiple materials | "Human speakers frequently use 就是/其实/啊 to preserve thinking process" | Rule |
| **Skill** | How to use Knowledge to accomplish a task | Expression Planning decides when to use repetition | Capability |
| **Generated Content** | Final output ContextOS produces | Script, title, hook, draft | Product |

### 3.2 Critical Boundaries

```
Raw Content ⊂ Data Layer
    ↓ extract
Observation ⊂ Analysis Layer
    ↓ validate (≥3 sources, ≥2 authors)
Knowledge Pattern ⊂ Knowledge Layer
    ↓ consumed by
Skill ⊂ Capability Layer
    ↓ invoked by
Generated Content ⊂ Output Layer
```

**Key Principle**: Knowledge does NOT generate content. Skills decide WHEN and HOW to use Knowledge. Prompts are just the vehicle.

## 5. Knowledge Pattern Schema

### 5.1 Conceptual Schema (Level 1)

```typescript
/**
 * KnowledgePattern — the fundamental unit of ContextOS Knowledge
 * 
 * A KnowledgePattern is not a "tip" or "suggestion".
 * It is a VERIFIED, REUSABLE RULE about content creation,
 * supported by evidence from real-world materials.
 */
interface KnowledgePattern {
  // ── Identity ──
  id: string                    // Unique identifier (e.g., "KP-EXP-002")
  knowledgeType: KnowledgeType  // expression | emotion | structure | anti_ai | platform
  name: string                  // Short, precise name (e.g., "口语连接词保留思考过程")
  
  // ── Content ──
  description: string           // One-sentence description of the pattern
  rule: string                  // The actual rule, written as an actionable principle
  
  // ── Examples ──
  examples: KnowledgeExample[]  // Positive examples from real materials
  counterExamples: KnowledgeExample[]  // Cases where this pattern does NOT apply
  
  // ── Applicability ──
  applicableContexts: string[]  // When this pattern works (e.g., ["情绪高点", "自我暴露"])
  applicablePlatforms: string[] // Platforms where validated
  applicableAudiences: string[] // Audiences where validated (future)
  
  // ── Evidence ──
  evidence: KnowledgeEvidence   // Proof that this pattern is real (see §6)
  
  // ── Status ──
  confidence: number            // 0-100, calculated from evidence (see §11)
  status: KnowledgeStatus       // observation | candidate | validated | active | deprecated | archived
  version: string               // Semver (e.g., "1.0.0")
  
  // ── Metadata ──
  createdAt: DateTime
  updatedAt: DateTime
  deprecatedAt: DateTime?
}
```

## 6. Evidence Model

### 6.1 Evidence Requirements

A KnowledgePattern **must NOT** enter the Knowledge Base based solely on:
- An LLM saying "this is a pattern"
- A single material showing the pattern
- Intuitive plausibility

### 6.2 Minimum Evidence Thresholds

| Status | Min Sources | Min Authors | Min Topics | Min Platforms |
|--------|------------|-------------|------------|---------------|
| Observation | 1 | 1 | 1 | 1 |
| Candidate | 2 | 1 | 1 | 1 |
| Validated | 3 | 2 | 1 | 1 |
| Active | 5 | 3 | 2 | 1* |

\* Platform minimum depends on knowledge type. Platform Knowledge requires 1; Expression Knowledge ideally 2+.

### 6.3 Evidence Diversity

**Critical Principle**: Same author using pattern 20 times ≠ 20 authors using pattern once.

| Metric | Formula | Weight in Confidence |
|--------|---------|---------------------|
| Source Count | Total materials showing pattern | 30% |
| Author Diversity | Distinct authors / Total sources | 35% |
| Topic Diversity | Distinct topics / Total sources | 20% |
| Platform Diversity | Distinct platforms / Total sources | 15% |

### 6.4 Evidence Quality Tiers

| Tier | Source Type | Quality Weight |
|------|-------------|----------------|
| S | High-engagement + High human-naturalness (P0.1.3 representative samples) | 1.0 |
| A | High-engagement OR High naturalness | 0.8 |
| B | Moderate engagement and naturalness | 0.6 |
| C | Low engagement but demonstrates pattern | 0.4 |
| D | Weak demonstration or ambiguous | 0.2 |

## 7. Knowledge Lifecycle

### 7.1 Lifecycle States

```
┌─────────────┐
│  Observation │  Initial detection; not yet validated
└──────┬──────┘
       │ Evidence count ≥ 2
       ▼
┌─────────────┐
│  Candidate   │  Preliminary validation passed; awaiting deeper evidence
└──────┬──────┘
       │ Evidence count ≥ 3 + Author diversity ≥ 2
       ▼
┌─────────────┐
│  Validated   │  Sufficient evidence; approved for use
└──────┬──────┘
       │ Passed human review or A/B test
       ▼
┌─────────────┐
│   Active     │  In production; Skills can reference
└──────┬──────┘
       │ New evidence conflicts OR pattern becomes template
       ▼
┌─────────────┐
│  Deprecated  │  Removed from production; historical record kept
└──────┬──────┘
       │ Grace period expired
       ▼
┌─────────────┐
│  Archived    │  Read-only; for audit trail
└─────────────┘
```

### 7.2 State Transition Rules

| From | To | Condition |
|------|----|-----------|
| Observation | Candidate | ≥2 supporting materials OR 1 high-quality material with strong evidence |
| Candidate | Validated | ≥3 materials from ≥2 authors, with explainable mechanism |
| Validated | Active | Human evaluation OR A/B test confirms effectiveness |
| Active | Deprecated | Counter-evidence ≥ 30% OR pattern detected as template by Audit |
| Deprecated | Archived | 30 days after deprecation (grace period) |
| Deprecated | Active | New evidence resolves previous concerns |
| Archived | (none) | Terminal state; read-only |

## 8. Promotion Rules

### 8.1 Candidate → Validated

**ALL** of the following must be true:
1. ≥ 3 independent source materials support the pattern
2. ≥ 2 distinct authors demonstrate the pattern
3. Pattern has a clear, explainable mechanism (not just correlation)
4. Pattern does NOT conflict with existing Active patterns (or conflict is documented)
5. At least one example has Evidence Quality ≥ B

### 8.2 Validated → Active

**ONE** of the following must be true:
1. **Human evaluation**: Domain expert reviews and approves
2. **A/B test**: Pattern-involved content outperforms control by statistically meaningful margin
3. **Correlation analysis**: Pattern presence correlates with high-engagement content (r > 0.3)

### 8.3 Active → Deprecated

**ANY** of the following triggers review:
1. Counter-evidence count ≥ 30% of supporting evidence
2. Audit system detects pattern used as mechanical template (>60% usage rate)
3. Platform algorithm change reduces pattern effectiveness
4. New evidence shows pattern context was incorrectly scoped

## 9. Counter-Evidence Mechanism

### 9.1 Counter-Evidence Schema

```typescript
interface CounterEvidence {
  id: string
  knowledgePatternId: string
  
  materialId: string            // Material that contradicts the pattern
  authorName: string
  quote: string                 // The contradicting excerpt
  explanation: string           // Why this contradicts the pattern
  
  // Was the pattern wrong, or just not applicable?
  contradictionType:
    | "context_mismatch"        // Pattern was applied in wrong context
    | "platform_change"         // Pattern no longer works on this platform
    | "audience_shift"          // Pattern no longer resonates with audience
    | "overuse_backlash"        // Pattern became template due to overuse
    | "genuine_refutation"      // Pattern was wrong to begin with
  
  createdAt: DateTime
}
```

### 9.2 Counter-Evidence Impact on Confidence

| Counter-Evidence Ratio | Action |
|----------------------|--------|
| < 10% | Minimal impact; note for review |
| 10-25% | Confidence reduction: -5 to -15 points |
| 25-40% | Confidence reduction: -15 to -30 points; trigger review |
| 40-60% | Pattern under investigation; temporarily freeze new usage |
| > 60% | Strong signal for deprecation |

## 10. Versioning

### 10.1 Version Format

Semver: `MAJOR.MINOR.PATCH`

- **MAJOR**: Pattern fundamentally changed (e.g., rule restructured)
- **MINOR**: New evidence added, confidencechanged, applicability expanded
- **PATCH**: Typo fix, example added, minor clarification

### 10.2 Version History Requirements

Every version change must record:
1. What changed (diff of rule, applicability, examples)
2. Why it changed (new evidence, audit finding, platform shift)
3. Who/what triggered the change (system, user, validation run)
4. When it occurred

### 10.3 Version and Status Relationship

| Status | Version Behavior |
|--------|-----------------|
| Observation | No versioning; direct edit |
| Candidate | v0.x.x (pre-release) |
| Validated | v1.0.0+ (release) |
| Active | v1.0.0+ (production) |
| Deprecated | Frozen at final Active version |
| Archived | Immutable |

## 11. Confidence Model

### 11.1 Confidence Components

Confidence is **not** a single truth value. It reflects ContextOS's **current trust level** in a knowledge pattern.

| Component | Source | Weight |
|-----------|--------|--------|
| Evidence Strength | sourceCount, authorQuality | 25% |
| Author Diversity | Distinct authors | 20% |
| Topic Diversity | Applicability breadth | 15% |
| Validation Results | A/B tests, expert review | 20% |
| Recency | Last evidence added | 10% |
| Contradiction Penalty | Counter-evidence ratio | -10% (max) |

### 11.2 Confidence Calculation (Recommended Approach)

```
baseScore = (
  evidenceStrength * 0.25 +
  authorDiversity * 0.20 +
  topicDiversity * 0.15 +
  validationResults * 0.20 +
  recencyScore * 0.10
)

contradictionPenalty = counterEvidenceRatio * 10

finalConfidence = max(0, min(100, baseScore - contradictionPenalty))
```

### 11.3 Confidence Thresholds

| Confidence | Meaning | Action |
|-----------|---------|--------|
| 0-20 | Tentative observation | Do not use in production |
| 20-40 | Candidate knowledge | Use with heavy caveats |
| 40-60 | Preliminary validation | Can inform human decisions |
| 60-80 | Moderate confidence | Safe for Skill consumption |
| 80-95 | High confidence | Primary reference |
| 95-100 | Very high confidence | Core knowledge; rarely contradicted |

### 11.4 What Confidence Is NOT

- Confidence ≠ Truth. A confidence of 80 means "ContextOS has strong evidence," not "this pattern is universally true."
- Confidence is **contextual**: a pattern may have confidence 90 on Douyin but 40 on Xiaohongshu.
- Confidence **decays** without new evidence. Patterns unused for 6+ months should be re-evaluated.

## 12. Knowledge Relations

### 12.1 Relation Types

| Relation | Meaning | Example |
|----------|---------|---------|
| `supports` | Using A makes B more effective | "口语连接词" supports "不完整表达" |
| `conflicts` | A and B should not be used together | "清单体" conflicts with "口语节奏" |
| `commonly_used_with` | A and B often co-occur in successful content | "自我暴露式开场" commonly_used_with "情绪突转" |
| `contraindicated_with` | A makes B less effective | "过度结构化" contraindicated_with "自我修正" |
| `variant_of` | A is a context-specific variant of B | "身体感受式表达" variant_of "情绪突转" |
| `prerequisite_for` | Understanding A helps apply B | "认知反转" prerequisite_for "反问式说服" |

### 12.2 Relation Usage in Retrieval

When Skills retrieve Knowledge:
1. Find initially relevant patterns
2. Follow `commonly_used_with` to add complementary patterns
3. Follow `contraindicated_with` to remove harmful patterns
4. Follow `supports` to strengthen reasoning
5. Use `conflicts` to prevent contradictory advice

## 14. System vs User Knowledge

### 14.1 Scopes

| Scope | Source | Visibility | Lifecycle |
|-------|--------|------------|-----------|
| `system` | ContextOS built-in | All users | ContextOS team manages |
| `project` | Learned within a project | Project owner | Project owner manages |
| `user` | Learned from user's content | Individual user | User manages |

### 14.2 Priority in Retrieval

When multiple knowledge sources exist:
1. **System knowledge** has highest priority (verified across many users)
2. **User knowledge** overrides system for individual preferences (lower confidence threshold)
3. **Project knowledge** overrides for project-specific patterns

### 14.3 Current Scope

P0.2 implements ONLY `system` knowledge. Project and user knowledge are schema-reserved for future phases.

## 15. Retrieval Architecture

### 15.1 Retrieval Methods (Concept Only)

#### Method 1: Structured Retrieval

```
platform = douyin
knowledgeType = expression
applicableContentType = emotional
```

**When to use**: Platform-specific, type-specific, well-structured queries.

#### Method 2: Semantic Retrieval (Future)

```
"用户主题：为什么成年人越来越不想解释"
→ Finds: 情绪共鸣、自我对话、认知反转、边界表达
```

**When to use**: Topic-based, creative, explorative queries.

#### Method 3: Hybrid Retrieval (Future — Recommended)

```
Structured Filter (platform, type, minConfidence)
  ↓
Semantic Search (topic relevance)
  ↓
Ranking (confidence, freshness, contradiction penalty)
```

### 15.2 Retrieval Interface (P0.2.2 Target)

```typescript
interface KnowledgeRetrievalQuery {
  // Structured filters
  knowledgeTypes?: string[]
  platforms?: string[]
  contentTypes?: string[]
  minConfidence?: number        // Default: 60
  status?: "active"            | "validated" | "candidate"
  
  // Semantic
  topic?: string                // Natural language topic description
  context?: string              // Current writing context
  
  // Ranking
  limit?: number                // Default: 10
  minEvidenceStrength?: number  // Default: 40
  
  // Relations
  includeCommonsWith?: boolean  // Also retrieve commonly_used_with patterns
  excludeConflictsWith?: string[]  // Exclude patterns conflicting with these
}

interface KnowledgeRetrievalResult {
  patterns: KnowledgePattern[]
  relations: KnowledgeRelation[]  // Relations among retrieved patterns
  packageContext?: string         // Which package these belong to
}
```

## 16. Ranking Concept

### 16.1 Ranking Factors

| Factor | Description | Weight |
|--------|-------------|--------|
| relevance | Topic/context match to query | 30% |
| confidence | Current confidence score | 20% |
| evidenceStrength | Quality and quantity of evidence | 15% |
| freshness | How recently evidence was added | 10% |
| platformFit | Match to target platform | 10% |
| audienceFit | Match to target audience | 5% |
| contradictionPenalty | Counter-evidence impact | -10% |
| overusePenalty | Pattern used too recently/frequently | -5% to -15% |

### 16.2 Anti-Overuse Mechanism

Patterns that are too frequently retrieved lose ranking priority to prevent "template fatigue":

```
adjustedRank = baseRank * (1 - overusePenalty)

overusePenalty = min(0.5, recentUsageCount / usageWindow)
```

Where `recentUsageCount` = usages in last 7 days, `usageWindow` = expected usage frequency.

## 17. Knowledge → Skill → Prompt Relationship

### 17.1 Critical Boundary

```
Knowledge (Database)
    ↓
Retriever (filters, ranks, selects)
    ↓
Context Builder (formats into injectable context)
    ↓
Skill (decides HOW to use, WHEN to use, HOW MUCH to use)
    ↓
LLM Prompt (final instruction vehicle)
```

### 17.2 Responsibilities

| Layer | Responsibility | Example |
|-------|---------------|---------|
| Knowledge Store | Store and serve raw patterns | "口语连接词 pattern + evidence" |
| Retriever | Find relevant patterns for query | "Pattern KP-EXP-002 is relevant" |
| Context Builder | Format knowledge for injection | "Use口语连接词 in 情绪高点, per KP-EXP-002" |
| Skill | Decide applicability + degree | Expression Planning: "Include 1-2口语连接词 steps" |
| LLM | Execute the decision | Generate text with口语连接词 |

### 17.3 What Can Go Wrong

| Anti-Pattern | Problem | Solution |
|-------------|---------|----------|
| Knowledge directly in Prompt | Prompt becomes enormous; knowledge changes require prompt edits | Knowledge referenced by ID, content injected at runtime |
| Skill bypasses Knowledge | Skill makes patterns up or uses outdated heuristics | Skill must cite knowledgePatternId |
| LLM receives too many patterns | Conflicting advice; over-optimization | Limit retrieved patterns to top 5-8 |
| Knowledge without Retrieval | Can't find relevant knowledge for new topics | Hybrid retrieval (structured + semantic) |

## 18. Real ContextOS Examples

### 18.1 Example 1: 口语连接词 Pattern

- Overuse (>60% of content) creates "煽情化" (P0.1.4 finding)
- Updated rule: "情绪突转适用于：故事自然发展到情绪节点 + 前后情绪形成真实对比 + 转折能够增强表达"

**Step 4 — Active Knowledge with Usage Constraints**:
Confidence: 65 (moderate, because contextual applicability varies)
Usage rule in Skill: "Apply to ≤40% of thoughtPath steps"

**Step 5 — Relation to Audit**:
Expression Audit issue type: `emotion_shift_excessive` — detects overuse

### 18.3 Example 3: 清单体 Anti-AI Pattern

**Step 1 — Observation**:
M005 (30条人生经验) and M012 (40个小tips) have lowest Human Naturalness scores.

**Step 2 — Observation → Candidate**:
Pattern: "高度结构化的编号列表（1-30, 1-40）是典型的AI味结构，缺乏自然表达的流动感。"

**Step 3 — Nuance Discovery**:
Counter-evidence: M003 uses 编号 naturally (口语化列举，非列表体)
Refined rule: "NOT all lists are AI-like. Lists become AI-like when: (a) items are overly complete, (b) transitions are absent, (c) summary is inevitable, (d) numbering exceeds ~10 items without breaks."

**Step 4 — Active Knowledge**:
Knowledge type: `anti_ai` (not `structure`)
Confidence: 75
Audit integration: `over_structured`, `predictable_structure`, `formulaic` issue types detect this.

## 19. Anti-Patterns: What Must NOT Become Knowledge

### 19.1 Forbidden Knowledge Types

| Category | Example | Why Not Knowledge |
|----------|---------|-------------------|
| Single-author catchphrase | M011's frequent use of "呀" | Not generalizable; bound to specific creator |
| One-time coincidence | A single video uses 5 consecutive questions | Cannot prove pattern without repetition |
| Platform operation jargon | "关注我", "设成特别关注" | Not expression knowledge; pure CTA |
| Specific personal experience | M004's marriage story | Cannot be templated; would violate truthfulness |
| Verbatim sentences | Full quotes from materials | Plagiarism risk; Knowledge stores rules, not sentences |
| Overfitted correlation | "Videos posted at 8pm perform better" | Spurious correlation; not content knowledge |
| Subjective preference | "Blue backgrounds feel calmer" | Not verifiable; not content knowledge |

### 19.2 Guardrails for Knowledge Entry

Before any observation becomes Candidate Knowledge, it must pass:

1. **Universality Test**: "Would this apply to a different creator on a different topic?"
2. **Verifiability Test**: "Can we find at least 3 independent examples?"
3. **Explainability Test**: "Can we explain WHY this pattern works?"
4. **Safety Test**: "If a creator uses this, does it risk plagiarism or inauthenticity?"
5. **Template Risk Test**: "If everyone uses this, does it become a new AI tell?"

## 20. Knowledge Health

### 20.1 Health Metrics

| Metric | Formula | Alert Threshold |
|--------|---------|----------------|
| Evidence Strength | Weighted average of source quality | < 40 |
| Usage Frequency | Uses per week | 0 for 30+ days |
| Success Rate | Usage where audit passes / total usage | < 60% |
| Contradiction Rate | Counter evidence / total evidence | > 30% |
| Freshness | Days since last evidence added | > 90 days |
| Redundancy | Overlap with other active patterns | > 80% |

### 20.2 Health Actions

| Health Status | Action |
|--------------|--------|
| Healthy | Continue active use |
| Aging (low freshness) | Trigger re-validation with new materials |
| Contradicted (high counter-evidence) | Deprecate pending review |
| Unused (no usage for 30+ days) | Consider archival |
| Overused (over-retrieved) | Apply ranking penalty; review for template risk |

## 26. Design Principles

1. **Knowledge should be small, clear, verifiable, and reusable** — never a giant methodology.
2. **Evidence is mandatory** — an LLM's intuition is not enough.
3. **Lifecycles are real** — knowledge can die or be reborn.
4. **Counter-evidence is first-class** — we must be able to disprove ourselves.
5. **Knowledge does not generate content** — Skills do, informed by Knowledge.
6. **Version everything** — traceability beats convenience.
7. **Prevent template pollution** — what works today can become tomorrow's AI tell.
