## 1. Executive Summary

Outcome Memory Foundation 为 ContextOS 建立了持久化记录结果（Outcome）的标准能力，闭合了从 Decision → Content → Outcome 的结果反馈环。

Outcome Memory 被定义为 `episodic` 类型的 Memory（观测事件快照），复用现有 Memory Layer 基础设施（MemoryRecord、MemoryStore、DatabaseMemoryRetriever），不修改 Prisma Schema。

## 2. Architecture

### 2.1 Layer Position

```
Outcome Observation (douyin/小紅書/manual)
       ↓
createOutcomeMemory()          ← Factory (validation + defaults)
       ↓
MemoryStore.create()           ← Persistence (existing)
       ↓
Database (MemoryRecord row)    ← No schema change — payload JSON
       ↓
retrieveOutcomeMemories()      ← Retrieval helpers (time-series pattern)
getOutcomeHistory()
getLatestOutcome()
       ↓
outcomeMemoryToContext()       ← Context Bridge
       ↓
ContextObject<OutcomeContextPayload>   ← Ready for Context Assembly
```

### 2.2 Outcome Memory vs Decision Memory

| 维度 | Decision Memory | Outcome Memory |
|------|-----------------|----------------|
| kind | `semantic` | `episodic` |
| type | `decision` | `outcome` |
| 语义 | 抽象决策知识 | 观测事件快照 |
| 时间特性 | 决策时间 | 观测时间 |
| 排序 | updatedAt / importance | **observedAt** |
| 可变性 | 可 superseded | 不可变快照 |
| Payload | DecisionMemoryPayload | OutcomeMemoryPayload |

### 2.3 Schema Reuse

Outcome Memory 复用 `MemoryRecord` 表，不需要任何 schema 变更：

```
MemoryRecord {
  id           — "out_" prefix + UUID
  kind         — "episodic"
  type         — "outcome"
  payload      — OutcomeMemoryPayload (JSON)
  scope        — derived from context IDs
  ownerId      — mandatory (isolation)
  version      — 1 (immutable snapshots)
  status       — "active" (always)
  createdAt    — factory set
  updatedAt    — factory set
}
```

## 3. Type System

### 3.1 OutcomeType

```typescript
export type OutcomeType =
  | 'performance'    // 综合效果/整体表现
  | 'engagement'    // 互动数据 (likes, comments, shares)
  | 'conversion'    // 转化 (sales, sign-ups, follows)
  | 'feedback'      // 定性反馈
  | 'publication'    // 发布事件
  | 'failure'       // 明确失败
  | 'milestone';    // 阶段性成就
```

### 3.2 OutcomeTargetType

```typescript
export type OutcomeTargetType =
  | 'content'       // 文案/作品
  | 'draft'         // 草稿
  | 'topic'         // 选题
  | 'decision'      // 决策
  | 'project';      // 项目
```

### 3.3 OutcomeMemoryPayload

```typescript
export interface OutcomeMemoryPayload {
  outcomeType: OutcomeType;        // ← REQUIRED
  targetType: OutcomeTargetType;   // ← REQUIRED
  targetId: string;                // ← REQUIRED
  metrics?: OutcomeMetric[];       // ← 量化指标
  qualitativeFeedback?: string[];  // ← 定性反馈
  summary?: string;                // ← 可读摘要
  expectedOutcome?: string;        // ← 预期结果（供对比）
  observedAt: string;              // ← REQUIRED (ISO 8601)
  attribution?: OutcomeAttribution; // ← 归因链接
}
```

### 3.4 OutcomeMetric

```typescript
export interface OutcomeMetric {
  key: string;      // e.g., 'views', 'likes', 'ctr'
  value: number;    // observed value
  unit?: string;    // 'count', 'percent', 'seconds', 'usd'
  source?: string;  // 'douyin', 'xiaohongshu', 'manual'
}
```

### 3.5 OutcomeAttribution

```typescript
export interface OutcomeAttribution {
  decisionId?: string;   // 关联决策
  strategyId?: string;   // 关联策略
  contentId?: string;    // 关联文案
  draftId?: string;      // 关联草稿
  topicId?: string;      // 关联选题
}
```

### 3.6 OutcomeMemory Type

```typescript
export type OutcomeMemory = MemoryRecord<OutcomeMemoryPayload>;
```

OutcomeMemory 是 MemoryRecord 的 type alias，不是新接口。这种设计确保零平行类型系统。

## 4. Factory

### 4.1 createOutcomeMemory()

```typescript
export function createOutcomeMemory(
  options: CreateOutcomeMemoryOptions
): OutcomeMemory;
```

**Auto-derivation Rules**:
- `id`: `out_` prefix + crypto.randomUUID()
- `scope`: explicit → topicId → projectId → global
- `kind`: `'episodic'`
- `type`: `'outcome'`
- `status`: `'active'` (immutable snapshots — always active)
- `confidence`: 0.7 (observed facts — reasonably high)
- `importance`: 0.7 (important for future learning)
- `version`: 1

**Validation**:
- outcomeType: must be valid OutcomeType
- targetType: must be valid OutcomeTargetType
- targetId: non-empty string
- observedAt: valid ISO 8601 date
- metrics (if present): each has non-empty key + valid number value
- attribution (if present): all fields are strings

## 5. Retrieval

### 5.1 retrieveOutcomeMemories()

```typescript
export async function retrieveOutcomeMemories(
  retriever: MemoryRetriever,
  params: OutcomeRetrievalParams,
): Promise<OutcomeMemory[]>;
```

- Returns outcomes sorted by `observedAt DESC`
- Post-filters by payload fields (targetType, targetId, outcomeType)
- Default limit: 50

### 5.2 getOutcomeHistory()

```typescript
export async function getOutcomeHistory(
  retriever: MemoryRetriever,
  params: { targetId: string; targetType: OutcomeTargetType; ... },
): Promise<OutcomeMemory[]>;
```

- Returns ALL observations for a specific target
- Time series — newest first (`observedAt DESC`)
- No limit by default (up to config max)

### 5.3 getLatestOutcome()

```typescript
export async function getLatestOutcome(
  retriever: MemoryRetriever,
  params: { targetId: string; targetType: OutcomeTargetType; ... },
): Promise<OutcomeMemory | null>;
```

- Returns the most recent observation for a target
- **Critical Design Note**: Retriever sorts by importance/confidence/updatedAt, not observedAt. So `getOutcomeHistory` fetches up to 100 records, sorts by observedAt in memory, and takes the first.

## 7. Design Decisions

### D1: Why Episodic (not Semantic)?

Outcome 是"观测到的事件快照"——某个时间点测量到的具体数值。它是具体发生的事（episodic），不是抽象知识（semantic）。

Decision = semantic（决策知识可以复用）
Outcome = episodic（观测记录必须按时间保留）

### D2: Why No Schema Change?

Outcome Memory 复用 MemoryRecord 表的 `payload` JSON 字段存储 OutcomeMemoryPayload。这避免了 schema migration，同时保留了完整的结构化查询能力（payload 中的字段在应用层过滤）。

### D3: Why Time-Series Sorting Layer?

MemoryRetriever 默认按 importance/confidence 排序——这对决策知识合适，但对 Outcome 不合适。Outcome 的最新值几乎总是按 `observedAt` 排序的第一个。

解决方案：retrieval helper 先获取充足记录（limit × 2），在内存中按 `observedAt DESC` 排序，再截取。

### D4: Why Attribution (not Foreign Key)?

Outcome 通过 ID 引用 Decision/Content/Draft——不建立数据库关系。原因：
1. 避免 schema 变更
2. 保持 Memory Layer 独立
3. 未来 P0.6.6 Context Graph 将建立真正的图关系

## 11. P0.6.5.1-R1 — Retrieval Hardening

### R1 Problem

Foundation 版本的 Outcome 检索存在完整性问题：

```
DatabaseMemoryRetriever
       ↓
MemoryStore.findMany()
       ↓ (retriever sorts by importance/confidence/updatedAt)
limit × 2  ←  brute-force oversampling
       ↓
Outcome post-filter  ←  in-memory type check
```

当 Memory 数据量增长后（如 100 条 Memory 中只有 10 条 Outcome，retrieve limit=50），最终只能得到 10 条 Outcome，**实际的 Outcome limit 被非 Outcome 数据"占据"了**。

此外：
- `getOutcomeHistory()` 默认抓取 100 条不够稳健
- `getLatestOutcome()` 通过"先取100条 → 内存排序 → 第一条"决定最新值，存在正确性边界

### R1 Solution

#### 方案：扩展通用 Memory Query（type 字段 DB 级过滤）

不创建新的 Retriever/Store/DTO，仅在通用 `MemoryQueryCriteria` 增加 `types?: string[]`：

```typescript
// MemoryQueryCriteria (memory-query.ts)
export interface MemoryQueryCriteria {
  // ... existing fields ...
  types?: string[];  // ← R1 addition: DB-level type filter
}
```

#### 数据流变化

```
retrieveOutcomeMemories()
       ↓
policy.types = ['outcome']   ←  DB-level type filter
       ↓
DatabaseMemoryRetriever.buildCriteria()
       ↓
MemoryQueryCriteria.types = ['outcome']
       ↓
PrismaMemoryStore.buildWhereClause()
       ↓
SQL: WHERE type = 'outcome'  ←  pushed to database
       ↓
Only outcome records returned
       ↓
Application-level filters (targetType, targetId, outcomeType — still in JSON payload)
```

#### Modified Files (R1)

| File | Change |
|------|--------|
| `src/memory/memory-policy.ts` | `MemoryPolicy.types?: string[]` field |
| `src/memory/persistence/memory-query.ts` | `MemoryQueryCriteria.types?: string[]` field |
| `src/memory/persistence/prisma-memory-store.ts` | `buildWhereClause()` type filtering |
| `src/memory/database-memory-retriever.ts` | `buildCriteria()` passes types from policy |
| `src/memory/memory-retriever.ts` | `InMemoryRetriever` type filtering |
| `src/memory/outcome-memory-retrieval.ts` | Pass `types: ['outcome']`, remove `limit×2`, bounded limits |
| `src/memory/index.ts` | `MAX_OUTCOME_HISTORY_LIMIT` (500) export |

### R1 Design Decisions

#### D-R1.1: Why Not New Retriever?

Outcome 检索是 Memory 检索的特化，不需要独立的 Retriever。通用 `types` 字段让所有 memory domain（Decision、Outcome、Future）都受益。

#### D-R1.2: Why Target Fields Stay at App Level?

`targetType`、`targetId`、`outcomeType` 存在于 `MemoryRecord.payload` JSON 中。本阶段不修改 Prisma Schema。后续 P0.6.5.x 数据量真正达到需要时，再设计 JSON 索引或专用 projection。

#### D-R1.3: Bounded History

`getOutcomeHistory()` 返回 **最多 `limit` 条**记录，不是无限拉取：
- 默认 `limit = 100`
- 最大 `limit = 500` (MAX_OUTCOME_HISTORY_LIMIT) → 超出时自动 clamp
- 文档明确：**不是 ALL 记录，而是 bounded history**

#### D-R1.4: Latest Correctness Boundary

`getLatestOutcome()` 的正确性边界：
- 默认窗口：最近 100 个 observations（retriever 排序后的前 100 个 outcome）
- 可配置窗口：通过 `limit` 参数，最大 500
- 超出窗口：不保证正确性
- 未来 P0.6.5.x: 需要 dedicated temporal index/projection 才能实现 unbounded 正确性
- **重要**：由于 observedAt 存在 JSON payload 中，Prisma/SQLite 无法可靠地进行 JSON 排序。因此本阶段采用 bounded window + 应用层排序方案。
