# 0. 你现在要做什么

你正在修改一个已经完成 MVP 的 ContextOS 项目。

**不要重新设计整个 ContextOS，不要推倒现有 Agent，不要重新搭建 AI 基础设施。**

本任务只完成 Human Expression Engine 的 **P0.1 Foundation**：

```text
现有 Content Strategy
        ↓

        ↓
Writing                   ← 消费 ExpressionPlan
        ↓

        ↓
```

> **先决定作者如何表达，再进行写作，并在写作后进行结构化表达审计和定向修正。**

# 4. 核心产品原则

## 4.1 Strategy 与 Expression 必须解耦

`ContentStrategy` 负责：

> 这篇内容说什么、为什么说、面向谁、重点是什么。

`ExpressionPlan` 负责：

> 这个作者准备如何思考、如何组织表达、如何推进情绪、如何使用节奏和具体性。

不要让 Writing Skill 自己重新推导全部内容策略。

---

## 4.2 Expression Planning 必须发生在 Writing 之前

正确顺序：

```text
Strategy
↓
Expression Planning
↓
Writing
```

而不是：

```text
Writing
↓
Humanization
```

---

## 4.3 Audit 不负责“全文改写”

Audit 的职责：

```text
发现问题
→ 定位问题
→ 解释问题
→ 给出 rewrite instruction
```

Rewrite 的职责：

```text
只修复指定问题
```

默认不得全文重写。

---

## 4.4 Truth First

为了自然度，禁止模型伪造：

```text
用户真实经历
真实日期
真实人物
真实对话
真实数据
真实事件
```

如果文本没有真实个人经历，可以使用：

```text
GENERAL_OBSERVATION
GENERIC_SCENE
FICTIONAL_EXAMPLE
```

但必须明确语义身份，不得伪装为用户本人真实经历。

---

## 4.5 不追求“AI 检测分数”

P0.1 不应把“AI Score 越低越好”作为产品目标。

目标是：

```text
Naturalness
Voice Consistency
Specificity
Rhythm
Thought Coherence
Emotional Authenticity
```

`AI pattern` 只是辅助诊断信号。

# 6. ExpressionPlan 数据协议

## 6.1 目的

建立一个稳定、可序列化、可注入 Writing Prompt 的表达规划协议。

建议放置位置：

```text
优先复用项目已有 schema/types 目录。
如果不存在，创建最小必要模块，例如：

src/lib/expression/types.ts
src/lib/expression/schema.ts
```

**不要新建一套重复的全局类型体系。**

---

## 6.2 推荐 TypeScript 类型

根据仓库现有 schema 技术栈实现。如果项目使用 Zod，优先 Zod + inferred TypeScript types。

推荐逻辑结构：

```ts
export type ExpressionPlan = {
  version: "1.0";

  speaker: {
    role?: string;
    relationshipToAudience?: string;
    authority?: "low" | "medium" | "high";
    emotionalDistance?: "close" | "medium" | "distant";
  };

  thoughtPath: Array<{
    step: number;
    mode:
      | "observation"
      | "memory_trigger"
      | "association"
      | "question"
      | "contradiction"
      | "realization"
      | "reflection"
      | "self_correction"
      | "digression"
      | "return";
    purpose: string;
  }>;

  emotionCurve: Array<{
    stage: string;
    emotion: string;
    intensity: number;
  }>;

  rhythm: {
    sentenceVariance: "low" | "medium" | "high";
    paragraphVariance: "low" | "medium" | "high";
    shortSentencePreference: "low" | "medium" | "high";
    pauseFrequency: "low" | "medium" | "high";
  };

  expression: {
    oralness: "low" | "medium" | "high";
    specificity: "low" | "medium" | "high";
    reflection: "low" | "medium" | "high";
    imperfectionTolerance: "low" | "medium" | "high";
  };

  opening: {
    mode:
      | "observation"
      | "question"
      | "scene"
      | "contradiction"
      | "direct_statement"
      | "personal_reflection";
    instruction: string;
  };

  conclusion: {
    mode:
      | "reflection"
      | "open_ended"
      | "echo"
      | "question"
      | "direct_takeaway";
    instruction: string;
  };

  constraints: {
    mustPreserve: string[];
    avoidPatterns: string[];
    truthConstraints: string[];
  };
};
```

这是逻辑参考，不得盲目复制。

**以当前项目已有类型风格为准进行适配。**

每个 pattern 至少包含：

```yaml

```

```yaml

```

**example 只是表达结构示例，不是要求模型机械复制。**


# 13. Audit 规则

Audit 必须重点检查：

## 13.1 Formulaic

例如高频模板表达：

```text
首先 / 其次 / 最后
值得注意的是
从某种意义上来说
归根结底
本质上
真正重要的是
更值得关注的是
```

注意：

**这些词不是绝对禁用。**

只有在频繁、机械或与上下文不匹配时才报告。

---

## 13.2 Generic Abstraction

检查：

```text
很多人
我们每个人
在这个时代
随着年龄增长
生活中总会
```

是否缺乏具体观察或有效信息。

---

## 13.3 Uniform Rhythm

检查：

```text
连续句长过度相似
连续段落结构相似
连续观点都是“结论 + 解释”
```

不要要求所有文章都必须高变化。

---

## 13.4 Over Structure

检查：

```text
每段都有明确小结
每个观点都有标准解释
所有过渡都非常完整
```

---

## 13.5 Thoughtless Transition

检查内容是否存在：

> 句子在逻辑上正确，但缺乏真实思考推进。

例如：

```text
A
→ 因此 B
→ 所以 C
→ 最终 D
```

但作者实际上没有新的观察、联想或转念。

# 14. expression-rewrite Skill

创建：

```text
skills/expression-rewrite/
```

职责：

> 根据 Audit 的问题，只修改指定范围。

---

## 14.1 Rewrite 输入

```text
Draft
Audit
ExpressionPlan
ContentStrategy
Platform
```

---

## 14.2 Rewrite 核心规则

```text
1. 保留核心观点。
2. 保留事实。
3. 保留用户提供的真实经历。
4. 只修改被 Audit 指出的区域。
5. 不要无理由重写整篇文章。
6. 不要增加未经证实的信息。
7. 不要添加虚假的第一人称经历。
8. 不要为了自然而故意写错字。
9. 不要为了自然而堆叠“其实、然后、就是、说实话”等口头禅。
10. 不要把一篇成熟自然的文本重新改坏。
```

---

# 15. Rewrite Strategies

针对不同 issue type 使用不同策略。

```text
formulaic
→ 替换或删除模板化连接，不改变语义

generic
→ 将抽象表达改为具体观察，但不得虚构事实

abstract
→ 优先具体化概念、动作、场景、结果

uniform_rhythm
→ 调整句子和段落长度分布

over_structured
→ 删除不必要的小结和显式连接

over_explained
→ 删除重复解释，保留核心意思

emotion_flat
→ 根据已有内容调整情绪表达，不凭空制造经历

voice_drift
→ 回到 ExpressionPlan / Persona

thoughtless_transition
→ 增加自然思维推进或改用隐性衔接

fake_specificity
→ 删除伪具体细节，恢复可信的泛化表达
```

# 19. Naturalness Score

P0.1 可以实现基础规则和 LLM judge，但不要引入复杂训练模型。

建议基础评分：

```text
naturalness
voiceConsistency
specificity
rhythm
thoughtAuthenticity
emotionalAuthenticity
```

每项：

```text
0–100
```

`overallScore` 可以使用简单加权平均，但权重应集中在一个配置文件中，而不是散落在代码各处。

例如：

```ts
const DEFAULT_EXPRESSION_WEIGHTS = {
  naturalness: 0.25,
  voiceConsistency: 0.15,
  specificity: 0.15,
  rhythm: 0.15,
  thoughtAuthenticity: 0.15,
  emotionalAuthenticity: 0.15,
};
```

这只是参考值。

**根据当前项目现有 evaluation 习惯进行适配。**

# 20. 不要建立“绝对 AI 味阈值”

P0.1 不能使用：

```text
if aiScore < 20 then success
```

作为唯一业务判断。

```text

```

但阈值必须：

```text

可调整
可测试
```

并且最终验收不依赖单一 score。

# 22. Prisma / 数据库策略

P0.1 **默认不要求新增数据库表。**

优先采用：

```text
Agent State
+ existing generation records
+ existing JSON storage
```

原因：P0.1 的目标是验证 Expression Engine 是否有效，而不是提前建设复杂的数据基础设施。

只有当现有系统明显需要持久化 ExpressionPlan，而且实现成本极低时，才考虑增加字段。

如果确实需要数据库变更：

1. 修改 Prisma schema。
2. 生成 migration。
3. 补 migration 测试或至少 schema validation。
4. 在最终报告中解释为什么必须增加。

禁止大规模数据库重构。

# 26. Error Handling

至少处理：

```text
Expression Planning LLM failure
Expression Plan schema failure
Audit LLM failure
Audit schema failure
Rewrite LLM failure
Rewrite schema failure
```

策略：

### Planning 失败

降级：

```text
继续 Writing，但 expressionPlan = undefined
```

不要阻塞整个内容生成流程。

### Audit 失败

降级：

```text
跳过 Rewrite
直接进入现有 Evaluation
```

### Rewrite 失败

保留原 Draft。

不要把空字符串或半成品覆盖原稿。

# 37. 推荐的实现接口

如果现有架构允许，推荐形成类似接口：

```ts
const expressionPlan = await runExpressionPlanning({
  topic,
  selectedAngle,
  audience,
  strategy,
  platform,
  contentType,
  persona,
  emotionArc,
});
```

然后：

```ts
const draft = await runWriting({
  ...existingWritingInput,
  expressionPlan,
});
```

然后：

```ts
const audit = await runExpressionAudit({
  draft,
  expressionPlan,
  strategy,
  platform,
  persona,
});
```

如果：

```ts
!audit.pass
```

执行：

```ts
const revisedDraft = await runExpressionRewrite({
  draft,
  audit,
  expressionPlan,
  strategy,
  platform,
});
```

最后继续现有 evaluation。

**如果项目现有 API 命名不同，不得为了匹配示例而大规模改名。**

# 38. 失败模式检查

开发完成后主动寻找以下问题：

## Failure A

ExpressionPlan 已生成，但 Writer 完全不消费。

## Failure B

Audit 总是给 80+，失去诊断意义。

## Failure C

Rewrite 每次都全文重写。

## Failure D

Humanization 和 Expression Rewrite 互相重复执行。

## Failure E

Expression Engine 一失败，整个 Content Agent 崩溃。

## Failure F

为了“真人化”凭空添加第一人称经历。

## Failure G

所有文本都被强行加入：

```text
其实
就是
说实话
你有没有发现
……
```

## Failure H

所有内容都使用同一种 thought pattern。

## Failure I

为了让文本“更像真人”，导致内容准确性下降。

## Failure J

ExpressionPlan 变成第二套 Content Strategy。

必须在实现后主动检查这些问题。
