# P0.6.5.4 — Outcome Aggregation Layer

> Deterministic, on-demand aggregation over Outcome Memory observations.

**Status**: Completed 2026-10-02  
**Author**: contentos team  
**Previous**: P0.6.5.3 (Outcome Alerting)  
**Next**: P0.6.6 (TBD)

## 1. Overview

P0.6.5.4 implements the **aggregation layer** on top of Outcome Memory. It provides deterministic, pure-function aggregation over immutable Outcome observations — computing statistics, time-series bucketing, and adjacent-window trend comparison.

### Core Principle

```
OutcomeMemory[]  (immutable facts)
       ↓
outcome-aggregation.ts  (pure functions)
       ↓
OutcomeAggregation / OutcomeAggregationSeries / OutcomeMetricTrend
```

### Design Tenets

| # | Principle |
|---|-----------|
| 1 | Outcome = immutable fact; Aggregation = derived / recomputable |
| 2 | All aggregation is **ON-DEMAND** — no persistence of derived results |
| 3 | **Pure functions** — same input produces same output |
| 4 | **No `Date.now()`** inside aggregation logic (determinism) |
| 5 | No LLM, no AI judgment, no network, no global state |
| 6 | No new Prisma models — aggregation NEVER writes back to DB |
| 7 | `NaN` / `Infinity` / `-Infinity` excluded from all calculations |
| 8 | Metric grouping: `metricKey + unit` (missing unit → empty string) |
| 9 | Time window: `[start, end)` — half-open interval on `observedAt` |
| 10 | Completeness is **HONEST** — bounded when retrieval limit may truncate |

## 5. Service Layer

### 5.1 OutcomeAggregationService Interface

```typescript
interface OutcomeAggregationService {
  aggregate(outcomes, params): OutcomeAggregation;
  aggregateTimeSeries(outcomes, params, granularity): OutcomeAggregationSeries;
  compareWindows(outcomes, params): OutcomeTrendResult;
}
```

### 5.2 Stateless Design

`OutcomeAggregationServiceImpl` is a **stateless** service — safe to use as a singleton. All methods are pure computations over their inputs.

### 5.3 Method Details

#### `aggregate(outcomes, params)`

1. Validates time window (throws on invalid)
2. Parameter-level filtering (owner, project, topic, targetType, targetId, outcomeType, time window)
3. Sorts by `observedAt` ASC for first/last tracking
4. Groups metrics by `(key + unit)`, excludes non-finite values
5. Computes all six statistics per group
6. Sorts results deterministically by `(metricKey, unit)`
7. Determines completeness

#### `aggregateTimeSeries(outcomes, params, granularity)`

1. Validates time window
2. Parameter-level filtering
3. Generates UTC day or week buckets within window
4. Computes per-bucket metric aggregations
5. Returns ordered bucket array

#### `compareWindows(outcomes, params)`

1. Validates current window
2. Calculates previous window (equal length, immediately before)
3. Aggregates both windows
4. Computes per-metric trends (delta, deltaPercent, direction)
5. Returns combined trend result

## 6. Entry Point

### 6.1 `aggregateOutcomeMemories(retriever, params, service?)`

Primary entry point that connects the existing Outcome Retrieval layer to aggregation:

```typescript
export async function aggregateOutcomeMemories(
  retriever: MemoryRetriever,
  params: OutcomeAggregationParams,
  service?: OutcomeAggregationService,
): Promise<OutcomeAggregation>
```

**Behavior**:
1. Builds `OutcomeRetrievalParams` from aggregation params
2. Calls `retrieveOutcomeMemoriesWithMetadata()` — retrieves outcomes AND scanning metadata (`OutcomeRetrievalMetadata`)
3. Passes outcomes through `service.aggregate()` — parameter-level filtering applied again
4. If `metadata.truncated === true`, forces `completeness = 'bounded'` regardless of match count

### 6.2 `aggregateOutcomeMemoriesTimeSeries()`

Time-series entry point with metadata-driven completeness:

```
aggregateOutcomeMemoriesTimeSeries()
  → retrieveOutcomeMemoriesWithMetadata()
  → MemoryRetriever → OutcomeMemory[] + OutcomeRetrievalMetadata
  → OutcomeAggregationService.aggregateTimeSeries()
  → if metadata.truncated: series.completeness = 'bounded'
```

Retrieval fetches outcomes across a bounded window (default: 500 records max). The time-series buckets are computed from whatever outcomes arrive within that window. If retrieval hits a safety bound before DB exhaustion, the entire series is marked `bounded`.

### 6.3 `compareOutcomeMemoriesWindows()`

Trend comparison entry point with full bounded-window enforcement:

```
compareOutcomeMemoriesWindows()
  → retrieveOutcomeMemoriesWithMetadata()
  → MemoryRetriever → OutcomeMemory[] + OutcomeRetrievalMetadata
  → OutcomeAggregationService.compareWindows()
  → if metadata.truncated:
      result.completeness = 'bounded'
      result.currentWindow.completeness = 'bounded'
      result.previousWindow.completeness = 'bounded'
```

The retrieval layer fetches up to `retrievalLimit` outcome records (covering both windows). Aggregation then filters by time windows. **Critical**: if the retrieval itself was bounded, ALL trend results — both windows and aggregate — are forced to `bounded` because we cannot guarantee the previous window observations are complete.

A missing previous-window observation is **NOT** interpreted as zero. It is reported as:
- `direction: 'unknown'`
- `previousValue: undefined`

This prevents false "up from zero" artifacts when data simply falls outside the retrieval window.

## 8. Completeness Determination

The aggregation result includes a `completeness` field that honestly reports whether the underlying retrieval was complete or bounded.

### 8.1 Metadata-Driven Completeness

**Completeness is determined from retrieval metadata, NOT from counting results.**

| Condition | `completeness` |
|-----------|----------------|
| Retrieval exhausted data source before any configured bound | `'complete'` |
| Retrieval stopped because caller limit or safety bound was reached | `'bounded'` |

The `OutcomeRetrievalMetadata` from `retrieveOutcomeMemoriesWithMetadata()` provides:

| Field | Meaning |
|-------|---------|
| `scannedRecords` | Total records examined by the retriever (ALL records passing DB-level filters) |
| `batchesFetched` | Number of batch queries executed (1 to MAX_OUTCOME_RETRIEVAL_BATCHES) |
| `truncated` | `true` when retrieval hit a bound before DB exhaustion |
| `exhausted` | `true` when DB returned fewer records than requested |

### 8.2 Key Distinction: matched ≠ scanned

**matched outcome count ≠ scanned record count**

The number of outcomes matching a specific `targetId` can be far smaller than the number of records scanned. **Completeness is based on `scannedRecords`, not `outcomes.length`.**

**Example**: 500 records scanned, only 20 matched a specific `targetId`. Even though `20 < retrievalLimit(500)`, this is still `bounded` because the safety bound stopped scanning. There may be more matching records beyond the scanned window.

### 8.3 Entry Point Enforcement

All three entry points (`aggregateOutcomeMemories`, `aggregateOutcomeMemoriesTimeSeries`, `compareOutcomeMemoriesWindows`) apply the same rule:

```typescript
if (retrievalResult.metadata.truncated) {
  result.completeness = 'bounded';
}
```

The standalone `OutcomeAggregationServiceImpl.aggregate()` method still computes a `completeness` estimate based on `resultCount vs retrievalLimit`, but the Entry Point always overrides this when metadata proves truncation occurred.

The `retrievalLimit` field is always exposed for transparency.

## 9. Metric Grouping Strategy

Metrics are grouped by a composite key: `metricKey + "\0" + unit`.

- Missing `unit` is normalized to empty string `""`
- This prevents cross-unit mixing (e.g., `views` in `count` vs `views` in `thousands`)
- Non-finite values (NaN, Infinity, -Infinity) are excluded from all calculations
- Empty metric arrays produce zero-valued aggregation (count=0, sum=0, avg=0, etc.)

**Grouping key format**: `"views "` (with empty unit) vs `"views count"` (with unit)

## 10. Time Window Semantics

All time windows are **half-open intervals**: `[windowStart, windowEnd)`

- Observed at exactly `windowStart` → **included**
- Observed at exactly `windowEnd` → **excluded**

**UTC Boundaries**:
- Day: `00:00:00.000Z` to next `00:00:00.000Z`
- Week: Monday `00:00:00.000Z` to next Monday `00:00:00.000Z` (ISO 8601 convention)

## 11. Trend Comparison

### 11.1 Window Calculation

Given a current window `[windowStart, windowEnd)`:

```
windowLength = windowEnd - windowStart
previousWindow = [windowStart - windowLength, windowStart)
```

Previous window has **equal length** and is **immediately before** current (no overlap).

### 11.2 Delta Calculation

| Scenario | `delta` | `deltaPercent` | `direction` |
|----------|---------|----------------|-------------|
| current > previous | positive | `(delta / |prev|) * 100` | `'up'` |
| current < previous | negative | `(delta / |prev|) * 100` | `'down'` |
| current === previous | 0 | 0 | `'flat'` |
| previous === 0 | delta | `undefined` (div-by-zeros) | based on current |
| either undefined | `undefined` | `undefined` | `'unknown'` |

### 11.3 Comparison Metric

Trends compare **`avg`** (arithmetic mean) between windows. This is stable and representative for most outcome metrics.

## 12. Filtering

### 12.1 Parameter-Level Filtering

`filterOutcomesByParams()` applies ALL specified filters. Never trusts caller's data:

- Owner isolation (mandatory)
- projectId match (if specified)
- topicId match (if specified)
- targetType match (if specified)
- targetId match (if specified)
- outcomeType match (if specified)
- Time window: `[start, end)` on `observedAt`

### 12.2 Defense-in-Depth

Even when the retrieval layer has already filtered, the aggregation service applies filtering again. This ensures correctness regardless of input source (retrieved, manually constructed, or stored).

## 20. R2 — Completeness & Trend Retrieval Hardening

**Status**: Completed 2026-10-02
**Base**: P0.6.5.4 Section 1-19 (105 tests)

### 20.1 Problem Statement

The initial aggregation implementation had a critical integrity gap: when retrieval hit the safety bound (500 records), the aggregation layer would still report `complete` if matched records were fewer than the limit. Additionally, trend comparison misinterpreted missing data as zero values rather than unknown.

### 20.2 Retrieval Metadata Interface

New interface `OutcomeRetrievalMetadata` exposes scanning statistics:

```typescript
export interface OutcomeRetrievalMetadata {
  scannedRecords: number;   // Total records examined (not just matches)
  batchesFetched: number;   // Number of batch queries executed
  truncated: boolean;       // True if retrieval hit a safety bound
  exhausted: boolean;       // True if DB returned fewer records than requested
}
```

### 20.3 Five Collection Cases

`collectOutcomeBatches` now accurately distinguishes:

| Case | Condition | truncated | exhausted |
|------|-----------|-----------|-----------|
| A | No records found | `false` | `true` |
| B | Partial batch (DB exhausted) | `false` | `true` |
| C | Caller limit reached mid-batch | `true` | `false` |
| D1 | Max batches, full last batch | `true` | `false` |
| D2 | Max batches, partial last batch | `false` | `true` |

### 20.4 Completeness Enforcement

**Entry Point Hardening** (`outcome-aggregation-entry.ts`):
- `aggregateOutcomeMemories()`: if `metadata.truncated` → `completeness = 'bounded'`
- `aggregateOutcomeMemoriesTimeSeries()`: same override logic
- `compareOutcomeMemoriesWindows()`: if truncated → ALL windows forced to `'bounded'`

**Rationale**: When retrieval is bounded, we cannot guarantee all records were returned — even if matched outcomes are fewer than the limit.

### 20.5 Trend Baseline Safety

A missing previous-window observation is **NOT** interpreted as zero or flat. It is reported as:
- `direction: 'unknown'`
- `previousValue: undefined`

This prevents false "up from zero" trends when data is simply missing.

### 20.6 Bug Fix: Trend Grouping Key

`computeTrends()` in `OutcomeAggregationServiceImpl` was constructing grouping keys with `buildGroupingKey(ma.metricKey, ma.unit)` — but `buildGroupingKey` didn't exist. The correct function is `metricGroupingKey({ key, unit })` from `outcome-aggregation.ts`.

**Fix**: Use `metricGroupingKey({ key: ma.metricKey, unit: ma.unit })` for proper key construction.

### 20.7 Test Coverage (R2 Additions)

16 new regression tests (`outcome-retrieval-metadata.test.ts`):

| Category | Tests | Description |
|----------|-------|-------------|
| A | 1 | scannedRecords reports total examined |
| B | 1 | Exhaustion when DB returns < batchSize |

| D | 1 | Correct batchesFetched count |

Key test scenarios:
