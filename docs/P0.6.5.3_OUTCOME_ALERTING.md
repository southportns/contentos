# P0.6.5.3 — Outcome Alerting

**Status:** COMPLETED
**Date:** 2026-10-02

## 1. Overview

Outcome Alerting is a deterministic alerting system built on top of Outcome Memory.

### Core Principles

- **Outcome = immutable fact** — Outcome is read-only observation record
- **Alert = mutable signal** — Alert is mutable lifecycle state machine
- **Deterministic evaluation** — Pure function, no DB/LLM/network calls
- **Deterministic dedup** — Fingerprint = hash(ruleId:outcomeId), UNIQUE constraint
- **Owner isolation** — Every query includes WHERE ownerId = ?
- **Optimistic concurrency** — version-based updateMany, OCC guarantee
- **Severity propagation** — Alert severity is inherited from the OutcomeAlertRule
- **Custom message templating** — Rules can define `messageTemplate` with `{{placeholder}}` substitution
- **Rule validation at service layer** — All rules validated before evaluation begins
- **Actionable query semantics** — `listActionable()` returns only `open` and `acknowledged` alerts

## 2. Architecture

```
OutcomeMemoryService (P0.6.5.2)
    → OutcomeMemory (immutable)
    → OutcomeAlertService.evaluateOutcome()
      → validateAlertRule() for each rule (pre-check)
      → OutcomeAlertEvaluator.evaluateOutcomeAgainstRules() (pure function, DB-free)
      → _createAlertIfNew() → severity inherited from rule, message rendered from template
    → OutcomeAlert (mutable signal)
    → OutcomeAlertStore (interface: create/getByFingerprint/list/listActionable/update)
    → PrismaOutcomeAlertStore → SQLite
```

## 3. Data Models

### OutcomeAlertRule
- enabled, severity, outcomeType/targetType/targetId filter, metricConditions (AND semantics)
- Optional `messageTemplate` — supports `{metricKey}`, `{actualValue}`, `{threshold}`, `{operator}` placeholders

### OutcomeAlert
- Rule + Outcome IDs, severity (inherited from rule), status, title, message, matchedConditions, timestamps, version, fingerprint
- Status state machine: open → acknowledged → {resolved|suppressed} (terminal)

### OutcomeAlertTransitionError
- Properties: `alertId`, `fromStatus`, `toStatus` — provides full context for debugging

### Prisma Schema
- 16 fields including UNIQUE fingerprint, status/ownerId indexes

## 4. Key Design Decisions

### 4.1 Severity Propagation
The alert's `severity` field is copied from `OutcomeAlertRule.severity` at creation time. Hardcoded values are never used.

### 4.2 Message Template Rendering
When a rule defines `messageTemplate`, the alert's `message` field is rendered by substituting placeholders with actual matched condition values:
- `{metricKey}` — the metric name
- `{actualValue}` — the observed value
- `{threshold}` — the rule threshold
- `{operator}` — human-readable operator label

When no template is defined, a default `metricKey=actualValue op threshold` format is used.

### 4.3 Rule Validation at Service Layer
`OutcomeAlertServiceImpl.evaluateOutcome()` calls `validateAlertRule(rule)` for each rule before evaluation begins. This prevents invalid rules from reaching the evaluator and ensures early failure with descriptive error messages.

### 4.4 Transition Error with AlertId
`OutcomeAlertTransitionError` now carries the actual `alertId` (not `'unknown'`), enabling callers to identify which specific alert failed to transition.

### 4.5 Actionable Query
`OutcomeAlertStore.listActionable(ownerId, filters?)` returns only alerts in `open` or `acknowledged` status (the actionable states). It accepts the same filter options as `list()` minus `status` (which is fixed).
