# P0.6.3.3-R2 — Supersede Atomicity Closure

## 概述

R2 修复了 R1（以及原始 P0.6.3.3）中 `supersedeDecision()` 操作的非原子性问题。在 R1 的实现中，替代操作分为"先持久化新决策、再更新旧决策"两步执行，如果旧决策更新失败（如 OCC 冲突），新决策已被持久化，造成脏数据残留。

R2 通过将整个替代操作封装在 **Prisma 事务**（`prisma.$transaction`）中，确保"创建新决策 + 更新旧决策为 superseded"两步要么同时成功，要么同时回滚。

## 架构变更

### Before (R1 — 非原子)

```
supersedeDecision():
  1. store.create(newDecision)     ← 新决策已持久化
  2. store.update(oldDecision)     ← 若失败，新决策已成孤儿
  return newDecision
```

### After (R2 — 原子事务)

```
supersedeDecision():
  store.supersede(old, new, owner, version):
    prisma.$transaction(async (tx) => {
      1. tx.memoryRecord.create(new)         ← 事务内
      2. tx.memoryRecord.updateMany(old)     ← 事务内
      if (updateMany.count === 0) throw      ← OCC 失败触发回滚
      return createdNew
    })
```

## 接口设计

### MemoryStore.supersede()

在 `MemoryStore` 接口中新增 `supersede()` 方法：

```typescript
supersede(
  oldRecord: MemoryRecord,        // 旧记录（已含 superseded payload）
  newRecord: MemoryRecord,        // 新记录
  authenticatedOwnerId: string,   // 认证用户 ID
  expectedVersion: number,        // 旧记录期望版本（OCC）
): Promise<MemoryRecord>;         // 返回持久化的新记录
```

**安全保证：**
1. OCC 校验（expectedVersion 必须匹配）
2. 授权校验（authenticatedOwnerId 必须拥有旧记录）
3. 类型校验（旧记录必须是 DECISION）
4. 原子性（单数据库事务）

### PrismaMemoryStore.supersede()

```typescript
async supersede(oldRecord, newRecord, authenticatedOwnerId, expectedVersion) {
  // Step 0: 事务前校验（OCC、Authorization）
  ...

  // Step 1-3: 原子事务
  const result = await prisma.$transaction(async (tx) => {
    const createdNew = await tx.memoryRecord.create({ data: ... });
    const updatedOld = await tx.memoryRecord.updateMany({
      where: { id, ownerId, version: expectedVersion },
      data: { ..., version: expectedVersion + 1 },
    });
    if (updatedOld.count === 0) throw new MemoryConcurrencyError(...);
    return createdNew;
  });

  return persistenceToMemoryRecord(result);
}
```

### DecisionMemoryServiceImpl.supersedeDecision()

重构后的 Service 层不再直接调用 `store.create()` + `store.update()`，而是调用 `store.supersede()`：

```typescript
async supersedeDecision(oldDecisionId, newDecision, authenticatedOwnerId, expectedVersion) {
  // Step 1: 获取并校验旧决策
  // Step 2: 校验新决策所有权
  // Step 3: 准备记录（supersedes 链接）
  // Step 4: 原子替代（委托给 store）
  return this._store.supersede(supersededRecord, newRecord, authenticatedOwnerId, expectedVersion);
}
```

## 设计决策

### 1. 事务在 Store 层而非 Service 层

理由：
- Service 层不应感知数据库事务语义
- Store 层（Persistence）负责事务管理和一致性保证
- 未来其他操作（如 batch update）可直接复用事务能力

### 2. OCC 双重校验

- 事务前校验：快速失败，减少无意义的事务开启
- 事务内校验（updateMany WHERE version）：真正的并发安全保证
- 不可省略事务内校验（防止 TOCTOU 竞态）

### 3. MockMemoryStore 的事务模拟

Mock 的 `supersede()` 使用 try/catch 包裹更新步骤：
- 成功：返回新记录
- 失败：删除刚创建的新记录 → 模拟 rollback

### 4. 新决策 Fresh Create（非 Update）

替代操作始终 **创建** 新决策记录（新 ID、新 version=1），而非更新已有记录。
原因：
- 决策不可变历史（决策一旦做出不修改）
- supersedes 链接通过 payload 建立关系
- 便于审计和版本追溯

## 安全模型

```
             supersede 安全保证
  ┌─────────────────────────────────────────┐
  │ 1. Authorization: ownerId 必须匹配       │
  │ 2. OCC: expectedVersion 必须匹配        │
  │ 3. Atomicity: 全有或全无                │
  │ 4. Isolation: 其他用户记录不可见         │
  │ 5. No leak: 失败不暴露记录存在性         │
  └─────────────────────────────────────────┘
```
