# 1. 验收标准回答

## Q1: ContextOS 当前到底有哪些 Context？

见 `P0.6.0_CONTEXTOS_CAPABILITY_MAP.md` §3。

**当前 Context 类型**：
1. Topic Context（topic/platform/audience/contentType/goal/tone/constraints — 7 维度）
2. Platform Context（platform 字段 + platformFit 评分）
3. Content Context（研究内容 + 指标 + 结构 + 情感）
4. User Context（WritingProfile 蒸馏画像）
5. Knowledge Context（24 KU + Evidence 链 + 语义检索）
6. Persona Context（创作人设）
7. Strategy Context（策略选择与角度选择）
8. Source Context（原始素材内容 — 用于非虚构约束）

**缺失 Context**：
- Intent Context（显式意图模型）
- Historical Decision Context（历史决策）
- Outcome Context（结果反馈）
- Cross-Project Context（跨项目记忆）

---

## Q2: 这些 Context 存在哪里？

| Context 类型 | 存储位置 | 持久化 |
|-------------|---------|--------|
| Topic Context | Prisma DB (Topic 表) | SQLite |
| Platform Context | Prisma DB + Constants | SQLite + 代码 |
| Content Context | Prisma DB (Content/ContentLibraryItem) | SQLite |
| User Context | Prisma DB (UserWritingProfile/Archive) | SQLite |
| Knowledge Context | Static JSON + 内存索引 + 嵌入持久化 | JSON + SQLite |
| Persona Context | Prisma DB | SQLite |
| Strategy Context | Prisma DB (ContentStrategy/Angle) | SQLite |
| Source Context | Prompt 参数（内存） | 不持久化 |

## Q3: Context 如何进入 AI？

见 `P0.6.0_CONTEXTOS_CAPABILITY_MAP.md` §13。

当前 Pipeline：
1. API Route 接收请求（含 topicId/strategyId）
2. Strategy Knowledge Retrieval（语义搜索 → KnowledgeContextBuilder → StrategyKnowledgeContext）
3. Generation Knowledge Retrieval（同理）
4. Prompt Assembly（各 Skill 独立组装）
5. LLM 调用（Vercel AI SDK）
6. 输出解析 + 持久化

**关键文件**：
- `skills/content-strategy/prompts.ts` — 策略 Prompt 组装
- `skills/writing/prompts.ts` — 写作 Prompt 组装
- `skills/evaluation/prompts.ts` — 评估 Prompt 组装
- `src/knowledge/context/generation-knowledge-context.ts` — 知识上下文编排

## Q4: Context 是否具有来源和生命周期？

**来源 (Provenance)**：
- Knowledge 层有完整链路：KU → Evidence → Content
- Decision 层来源不完整：Strategy 审批有记录但无决策上下文
- Angle/Draft 来源明确但无结构化生命周期

**生命周期**：
- Capture: PARTIAL（多入口采集，但非统一 Context Capture API）
- Normalize: PARTIAL（Skill 层 Zod 校验 + 结构化输出）
- Store: YES（Prisma + JSON）
- Retrieve: YES（Repositories + Search）
- Apply: YES（Prompt 注入）
- Evaluate: YES（6 维评估）
- Update: PARTIAL（版本链 + 蒸馏画像）
- Learn: MISSING（无闭环学习）

---

## Q5: Context 是否能够被更新？

| Context 类型 | 更新能力 | 机制 |
|-------------|---------|------|
| Draft | YES | 版本链（新 Draft 不覆盖旧版） |
| Strategy | PARTIAL | upsert（重置审批状态） |
| Evaluation | NO | 每次生成新的 1:1 关联 |
| Persona | YES | CRUD API |
| Knowledge | NO | JSON 硬编码，无法运行时更新 |
| UserWritingProfile | YES | 版本递增蒸馏 |
| AgentRun | NO | 追加式记录 |
| Angle Status | YES | updateAngleStatus |

---

## Q6: 用户行为是否形成 Memory？

**部分形成**：
- 风格偏好 → UserWritingProfile（蒸馏）
- 最终内容选择 → UserContentArchive
- 精修行为 → Draft.changeReason + refineChanges
- 策略审批 → approvalStatus
- Humanization 采用 → adopted: Boolean

**未形成**：
- 角度选择决策未记录上下文
- 人工编辑模式（如"用户总是删掉第三段"）
- 跨项目的偏好迁移
- 决策结果与内容效果的关联

---

## Q7: Decision 是否被记录？

**当前 Decision 记录**：

| Decision | 记录方式 | 完整度 |
|----------|---------|--------|
| 策略审批 | approvalStatus + rejectionReason | ★★★☆☆ |
| 角度选择 | Angle.APPROVED 状态 | ★★☆☆☆ |
| 人性化采用 | adopted: Boolean | ★★☆☆☆ |
| 精修审核 | change-review accept/reject | ★★★☆☆ |
| 人工编辑 | Draft.changeReason (文本) | ★★☆☆☆ |
| 终稿保存 | UserContentArchive | ★★★☆☆ |

**缺失**：统一的 Decision 模型，包含 context（为什么决定）、alternatives（放弃了什么）、outcome（决定结果如何）。

---

## Q8: Outcome 是否能够反馈回来？

**不能。** 这是系统最大的闭环缺失：

- 无 Outcome 数据模型
- 无 Outcome 采集 API
- 无 Publication 追踪
- 无 Performance vs Prediction 对比
- 无反馈驱动的知识/策略更新

## 3.1 路线图

| Phase | 名称 | 预计工作量 | 依赖 |

| **P0.6.7** | End-to-End Context Loop | Large | All above |

## 3.2 Phase 描述

### P0.6.1 — Context Object Foundation
**目标**：定义统一 Context 抽象层，建立 Context Object Model 的类型系统和接口。

**范围**：
- 定义 `ContextObject` 抽象接口
- 定义 `Identity/Intent/Knowledge/Content/Evaluation/Decision/Outcome/Memory` 子类型
- 实现 Context Factory 模式
- 建立 Context 生命周期管理接口
- **不**修改数据库 Schema
- **不**修改现有业务逻辑

### P0.6.2 — Context Assembly Engine
**目标**：统一 Prompt 上下文组装逻辑，解决 Context Pollution 和 Prompt 膨胀问题。

**范围**：
- Context Builder Pipeline
- Context Priority/Quota 管理
- Knowledge Base CRUD（迁移 JSON 到 DB）
- 统一 Context 注入接口

### P0.6.3 — Memory Layer
**目标**：实现 4 层 Memory 架构。

**范围**：
- Static Memory: WritingProfile + 品牌画像
- Dynamic Memory: Active Context + 近期历史
- Episodic Memory: 决策/事件序列
- Semantic Memory: 语义知识（复用现有 Semantic Layer）

### P0.6.4 — Decision Memory
**目标**：记录并利用用户的每一个决定。

**范围**：
- Decision 实体模型
- Decision Context 捕获（为什么/放弃了什么）
- Decision Pattern 学习（"用户偏好 X over Y"）
- 基于 Decision 的默认建议

### P0.6.5 — Outcome Loop
**目标**：闭环学习。

**范围**：
- Outcome 数据采集 API
- Performance vs Prediction 分析
- 自动知识/策略更新
- 反馈驱动的 Prompt 优化

### P0.6.6 — Context Graph
**目标**：完整来源链与关系网络。

**范围**：
- KU 间关系模型
- 内容来源图谱
- 决策-结果关联图
- 图查询接口

### P0.6.7 — End-to-End Context Loop
**目标**：全链路验证。

**范围**：
- 从 Outcome 到 Knowledge 的自动更新
- 跨 Project 学习验证
- Context Pipeline 压力测试
- 完整 E2E 验收

# 6. P0.6.0 Conclusion

## 当前 ContextOS 的真实能力边界

**ContextOS 是一个处于转型期的系统**：
- 生成能力 (Generation Layer) 已成熟度极高
- 知识能力 (Knowledge Layer) 框架完备但规模受限
- Context 能力分散在各处，缺乏统一抽象
- Memory/Decision/Outcome 三点是明确的架构空白

## 最大的架构 Gap

1. **Outcome Loop 缺失** — 系统无法从最终结果学习，所有优化都依赖人工蒸馏
2. **Decision Memory 不完整** — 最有价值的学习信号（用户为什么选择 A 不选 B）未被捕获
3. **Context Object 无抽象** — 各层 Entity 独立运作，缺乏统一的上下文组装和管理机制

## 下一阶段应该开发什么

**优先级排序**：
1. P0.6.1 Context Object Foundation — 建立统一抽象
2. P0.6.2 Context Assembly Engine — 统一上下文注入 + 知识库 CRUD
3. P0.6.3 Memory Layer — 分层记忆架构
4. P0.6.4 Decision Memory — 决策记忆系统
5. P0.6.5 Outcome Loop — 闭环学习

## 是否可以进入 P0.6.1

**YES。**

P0.6.0 已完整完成：
- 能力地图清晰
- 架构债务明确
- Gap 分析有代码证据支撑
- Roadmap 7 Phase 设计完成
- 无代码副作用

**推荐立即进入 P0.6.1 — Context Object Foundation。**
