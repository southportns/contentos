# P0.6.2 — Context Assembly Engine

## Overview

Context Assembly Engine 是一个受约束、可解释、可追踪的上下文组装引擎，负责将分散的 ContextObject 集合转化为结构化的、可直接注入 Prompt 的文本输出。

**核心问题**：解决了 Context 的筛选、排序、去重、预算控制及序列化问题。

**架构定位**：

```
Context Sources → Retrieval → Selection → Ranking → Deduplication → Budget → Package → Serialization → Prompt
```

## Architecture

### Pipeline Stages

| Stage | Module | Responsibility |
|-------|--------|---------------|
| **Select** | `context-selector.ts` | 基于 Kind 和 Scope 边界初步筛选（global/project/topic/unknown） |
| **Rank** | `context-priority.ts` | 基于多维度加权评分的可解释排序 |
| **Dedup** | `context-dedup.ts` | 基于确定性指纹的去重 |
| **Budget** | `context-budget.ts` | Token 估算与预算截断 |
| **Package** | `context-package.ts` | 按 Kind 分组构建结构化包 |
| **Serialize** | `context-serializer.ts` | 转换为 Prompt 可用的文本 |

### Explainable Ranking

排序基于 5 个维度的加权评分：

| Modifier | Weight | Description |
|----------|--------|-------------|
| Base Priority | 20-100 | Kind 的基础优先级（identity=100, intent=90, strategy=80, ...） |
| Purpose | +25 (+ position bonus) | 与当前用途的相关性，列表位置靠前的额外最多 +20 |
| Confidence | +15 (tiered) | 高置信度(≥0.8)=+15, 中(≥0.5)=+7.5, 低(>0)=+3 |
| Relevance | +20 (topic) / +10 (project) | Topic 匹配 +20, Project 匹配 +10 |
| Recency | +10 (decaying) | 时间衰减（半衰期 24h），最远衰减至 0 |
| Required | +1000 | Required kind 确保排名最高 |

每个 `ScoredContext` 包含 `reasons[]` 数组，记录所有对分数有贡献的因子，实现完全可解释。

### Deterministic Deduplication

使用确定性指纹进行去重：

- **Fingerprint**: `kind:type:source` 或 `kind:type:source:id`
- 相同指纹的上下文只保留第一个
- 结果可复现、可测试

### Token Budgeting

基于字符比例的确定性 Token 估算：

- `CHARS_PER_TOKEN = 2.5`（中英混合场景：中文 ~1.5 chars/token，英文 ~4 chars/token，取 2.5 作为合理均值）
- 估算方法：序列化上下文_kind + type + payload values 后除以 CHARS_PER_TOKEN，向上取整
- 预算分配按排名优先级降序
- `requiredKinds` 机制确保核心上下文在预算紧张时不会被静默删除
- 预算包含三层约束：`maxTokens`、`maxContexts`、`maxPerKind`

### Shadow Integration

Writing Skill 作为首个接入点，采用 **Shadow Integration** 模式：

- Assembly Shadow 生成序列化 Context Preview（通过 `serializeContextPackage()`）
- **当前生产 Writing Prompt 仍由原有参数路径驱动**（WRITING_PROMPT function + knowledgeContext）
- Shadow 不改变 Prompt Source of Truth
- 无破坏性变更：原有的 `knowledgeContext` 路径保持不变
- 验证完成后可无缝切换为正式集成

> **P0.6.2-R1 = Shadow Observation**
> 正式 Prompt Replacement 不属于当前 Phase。

## Usage

```typescript
import {
  assembleContexts,
  buildContextPackage,
  serializeContextPackage,
} from '@/context/assembly';

// 1. 组装上下文
const result = assembleContexts({
  contexts: [intentCtx, strategyCtx, knowledgeCtx, identityCtx],
  purpose: 'writing',
  maxTokens: 5000,
  projectId: 'proj_1',
  topicId: 'topic_1',
});

// 2. 构建结构化包
const pkg = buildContextPackage(result);

// 3. 序列化为 Prompt 文本
const serialized = serializeContextPackage(pkg, { includeHeader: true });

// 4. 注入 Prompt
const prompt = `${basePrompt}\n\n## Context Assembly\n${serialized}`;
```

## Design Principles

1. **Constrained** — 明确的边界和限制，不做超出职责的事
2. **Explainable** — 每个决策都有可追溯的原因
3. **Deterministic** — 相同输入始终产生相同输出
4. **Non-breaking** — Shadow Integration 不破坏现有业务
5. **Composable** — 每个阶段独立可测、可替换

## Scope Inference (P0.6.2-R1.1)

`resolveContextScope()` resolves effective scope using the following priority:

1. **Explicit scope** — `provenance.scope` is used as-is (highest priority)
2. **Topic scope inferred** — `topicId` present, no explicit scope → `'topic'`
3. **Project scope inferred** — `projectId` present, no `topicId` → `'project'`
4. **Global scope** — neither `topicId` nor `projectId` → `'global'`

This prevents cross-topic leakage: within Project P1, Topic T1's assembly will
exclude Contexts from Topic T2 (even though both share the same Project).

**Adapter behavior**: Topic, Strategy, Draft, and Evaluation adapters naturally
infer `'topic'` scope because they carry `topicId`. Knowledge contexts stay
`global` because they have no `topicId`/`projectId` binding.

## Production Scope Propagation (P0.6.2-R1.2)

Scope information flows from the real Writing production request through
the skill schema into Context Assembly Shadow:

```
Writing Production Request (API / page)
  → WritingInput { projectId?, topicId? }
  → skills/writing/index.ts (runWritingShadow)
  → buildShadowContexts() — sets provenance with scope
  → resolveContextScope() — infers scope from topicId/projectId
  → isScopeCompatible() — enforces topic/project boundary
  → Scope-aware observation (metadata only)
```

**Key points**:
- `projectId` and `topicId` are **optional** in `WritingInput` — backward compatible
- Shadow uses scope for **observation only** — does NOT modify production Prompt
- Intent/Strategy/Identity contexts inherit `topicId` → inferred as `'topic'`
- Knowledge context keeps `topicId=null` → inferred as `'global'`
- Global knowledge always passes through, even in topic-scoped assemblies

## Non-Goals

- 不做 LLM 调用（这是 Skill 层的职责）
- 不做持久化（这是 Repository 层的职责）
- 不做实时缓存（未来优化）
- 不实现所有 Retriever（P0.6.2 仅 Knowledge）
