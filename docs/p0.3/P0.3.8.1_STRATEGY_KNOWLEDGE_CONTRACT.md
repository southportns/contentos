## 1. Purpose

P0.3.7 建立了 Knowledge Context 并接入 Writing 层。P0.3.8 的目标是将 Knowledge Context 扩展到 Strategy 层。本阶段（P0.3.8.1）的核心问题是：

> **Content Strategy 层应该接收什么样的 Knowledge 数据？**

当前 Strategy 层的 `runContentStrategy()` 是纯 LLM Prompt 驱动，没有任何 Knowledge 输入。本阶段定义了 Strategy 层消费 Knowledge 的数据契约（Contract），为下一阶段（P0.3.8.2 Strategy Knowledge Retrieval）奠定基础。

### 1.1 本阶段目标

- 定义 `StrategyKnowledgeContext` 类型 — Strategy 层消费的数据视图
- 定义 `StrategyKnowledgeItem` 类型 — 单个知识项的 Strategy 视图
- 实现 `toStrategyKnowledgeContext()` — 从 KnowledgeContext 到 Strategy 数据的纯函数转换
- 编写完整的 Contract 测试套件
- 验证与 P0.3.7 的向后兼容性

### 1.2 本阶段不做

- ❌ 不实现 Strategy Retrieval（留给 P0.3.8.2）
- ❌ 不修改 Strategy Prompt（留给后续阶段）
- ❌ 不修改 Strategy API（留给后续阶段）
- ❌ 不修改 runContentStrategy（留给后续阶段）

## 2. Design Principles

| 原则 | 说明 |
|------|------|
| **Minimal** | 只暴露 Strategy 决策需要的字段 |
| **Read-only** | 转换纯函数，不修改源 KnowledgeContext |
| **Status-preserving** | validated/candidate 状态必须保留，绝不能转换 |
| **Retrieval-independent** | Strategy 不感知 threshold/topK/method 等检索内部数据 |
| **Prompt-independent** | Contract 不包含任何 prompt text，数据和序列化分离 |
| **Deterministic** | 相同输入 → 相同输出 |
| **No retrieval dependency** | Contract 类型不依赖任何检索服务类型 |

## 3. Contract

### 3.1 完整 TypeScript 类型定义

**文件**: `src/knowledge/context/strategy-knowledge-context.ts`

#### StrategyKnowledgeItem

```typescript
export interface StrategyKnowledgeItem {
  /** Knowledge Unit display name */
  name: string;

  /** Original knowledge text — never modified, never summarized */
  text: string;

  /** Knowledge category — reuses existing KnowledgeCategory type */
  category: KnowledgeCategory;

  /** Knowledge level — reuses existing KnowledgeLevel type */
  knowledgeLevel: KnowledgeLevel;

  /**
   * Knowledge Unit status — MUST be preserved as-is.
   * Never convert candidate → validated or vice versa.
   */
  status: KUStatus;

  /**
   * Knowledge Unit confidence level.
   * Represents knowledge reliability, NOT query relevance.
   */
  confidence: ConfidenceLevel;

  /**
   * Semantic similarity score from retrieval.
   * Range: 0.0 ≤ similarity ≤ 1.0
   * Represents QUERY RELEVANCE, not truth score.
   * Strategy MUST NOT interpret this as truth score.
   */
  similarity: number;

  /**
   * Number of evidence items associated with this Knowledge Unit.
   * Optional — provides evidence scale reference only.
   * MUST NOT be used as automatic trust calculator.
   */
  evidenceCount?: number;
}
```

#### StrategyKnowledgeContext

```typescript
export interface StrategyKnowledgeContext {
  /**
   * Primary Knowledge Items — most relevant to the strategy query.
   * Preserved in Builder order (P0.3.7.3 deterministic sort).
   * May be empty.
   */
  primaryKnowledge: StrategyKnowledgeItem[];

  /**
   * Supporting Knowledge Items — secondary relevance.
   * Preserved in Builder order (P0.3.7.3 deterministic sort).
   * May be empty.
   */
  supportingKnowledge: StrategyKnowledgeItem[];
}
```

### 3.2 设计选择：独立 View vs 直接复用 KnowledgeContext

**问题**: Strategy 应该直接收到 KnowledgeContext，还是收到一个专门的 StrategyKnowledgeContext？

**结论**: 创建独立的 `StrategyKnowledgeContext` View。

**理由**:

1. **TypeScript 边界安全** — Strategy 代码无法访问 knowledgeId、retrievalReason 等内部字段（编译期强制，而不仅是序列化层过滤）
2. **依赖方向清晰** — Knowledge Layer → Strategy-specific View → Strategy Skill（单向依赖）
3. **未来扩展灵活** — 如果 Strategy 需要不同的字段组合或额外的策略层字段，View 可以独立演化
4. **与 P0.3.7 不冲突** — Writing 继续使用完整的 KnowledgeContext + Serializer 路径，不受影响

**注意**: P0.3.8.0 Reconnaissance 曾推荐方案 A（直接复用 KnowledgeContext），本阶段经过更深入的类型分析后，决定创建专用 View。两者功能等价，但 View 方案提供更强的编译期保障。

## 6. Candidate Semantics

### 6.1 状态保留规则

```
Contract 层只负责「表达」，不负责「决定」
```

| 场景 | Contract 行为 |
|------|--------------|
| `status = 'validated'` | 原样保留为 `StrategyKnowledgeItem.status = 'validated'` |
| `status = 'candidate'` | 原样保留为 `StrategyKnowledgeItem.status = 'candidate'` |
| `status = 'candidate'` + `confidence = 'high'` | 合法状态 — candidate 不因高置信度转为 validated |
| `status = 'validated'` + `confidence = 'low'` | 合法状态 — validated 不因低置信度降级 |

### 6.2 Status 与 Confidence 独立

```
status  ≠ confidence

它们是两个完全独立的维度：
  status     = 知识单元的验证状态（validated / candidate）
  confidence = 知识单元的置信度（high / medium / low）

一个 candidate 可以有 high confidence — 这表示「知识内容看起来可靠，
但尚未经过人工验证」。
```

### 6.3 Candidate 过滤策略（留给 P0.3.8.2）

Contract 层不对 candidate 做任何过滤：
- 是否让 candidate 进入 Strategy → P0.3.8.2 的 Retrieval Policy 决定
- 是否在 Strategy Prompt 中标注 candidate → Prompt Assembly 层决定
- 本阶段 Contract 层保证：两种状态都能被正确表达

## 7. Empty / Failure 设计

### 7.1 三种语义区分

| 场景 | 含义 | 返回值 |
|------|------|--------|
| **Empty** | retrieval 成功，0 结果 | `StrategyKnowledgeContext { primaryKnowledge: [], supportingKnowledge: [] }` |
| **Failure** | retrieval 错误 | 由 orchestration 层返回 `null`（不进入 Contract） |
| **Absent** | 未提供 retrieval 结果 | 由 skill 层传 `undefined`（不进入 Contract） |

### 7.2 Empty Context 是合法的

```
primaryKnowledge: []
supportingKnowledge: []
```

- 不是错误，不是异常
- Strategy 继续正常运行（纯 LLM 推理）
- 与 P0.3.7.5 (Writing) 的降级语义保持一致

## 8. Ordering

### 8.1 顺序保存

Adapter **不重新排序**：

- `primaryKnowledge` — 保持 Builder (P0.3.7.3) 的确定性排序
- `supportingKnowledge` — 保持 Builder (P0.3.7.3) 的确定性排序

Builder 排序规则（P0.3.7.3）：
1. Status: validated 优先 candidate
2. Similarity: 高优先
3. Confidence: 高优先
4. Evidence Count: 多优先
5. Tie-breaker: knowledgeId 字母顺序（确定性）

### 8.2 Primary / Supporting 分界

- 与 Builder (P0.3.7.3) 一致：≤3 items 全部 primary，>3 items 按 60% primary
- Adapter 不重新分类
