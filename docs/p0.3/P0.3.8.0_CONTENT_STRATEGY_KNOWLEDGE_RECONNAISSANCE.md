# P0.3.8.0 — Content Strategy Knowledge Context Reconnaissance & Architecture Design

**Date**: 2026-09-14
**Phase**: P0.3.8.0 — RECONNAISSANCE & DESIGN ONLY
**Status**: COMPLETE

---

## 1. Executive Summary

P0.3.8 的目标是将 Knowledge Context 从 Writing 层扩展到 Strategy 层，形成完整的 **Knowledge → Strategy → Human Approval → Writing → Human Expression** 链路。当前 Knowledge Context 仅在 Writing 阶段注入（P0.3.7），Content Strategy 和 Angle Generation 仍然纯 LLM Prompt 驱动。

本阶段只做侦察与设计，不修改任何生产代码。

**一句话回答 P0.3.8 为什么要做：**

> Knowledge Context 可以帮助策略层识别历史高表现模式、提供已验证的结构/钩子/情感模式作为参考证据，让策略提案有知识依据而非纯想象，同时严格遵守 Human Approval 边界 — Knowledge 提供建议，人类做最终决策。

## 2. Current Architecture（真实架构图）

```
User Topic Input
      ↓
Topic Research (skills/topic-research)
      ↓
TopicProfile { topic, category, keywords, coreQuestions, potentialAngles, platform }
      ↓
Angle Generation (skills/angle-generation)
  Input:  topic + topicProfile + viralPatterns + audienceInsights
  Output: ContentAngle[] (5 angles with title, angle, reasoning, viralScore, difficulty)
      ↓
Human Angle Selection (UI: /create/angles)
  workflowActions.setSelectedAngle(angle)     ← ANGLE APPROVAL POINT (UI层)
      ↓
Content Strategy + Writing Pipeline (/create/generate)
  ┌──────────────────────────────────────────────────────┐
  │ handleGenerate():                                    │
  │   Step A: strategyHook.generate() → /api/strategy    │
  │           → runContentStrategy()                     │
  │           → ContentStrategy {title, hook, structure, │
  │              keyArguments, emotionalArc, CTA, tone}   │
  │   Step B: writingHook.generate() → /api/writing      │
  │           → retrieveKnowledgeContextForGeneration()  │  ← ONLY here
  │           → runWriting({...input, knowledgeContext}) │
  │   Step C: eval + strategyEval + riskAnalysis (并行)  │
  └──────────────────────────────────────────────────────┘
      ↓
Refinement (/create/refine) — human editing            ← FINAL DRAFT APPROVAL POINT
      ↓
Final Output
```

**关键发现**：

| 发现 | 说明 |
|------|------|
| Strategy 显式 Human Approval 缺失 | `/create/generate` 中 Strategy 和 Writing 在一个 `handleGenerate()` 中顺序执行，中间无用户审批停顿 |
| Angle Approval 在 UI 层实现 | `/create/angles/page.tsx` 用户点击选择角度后点击"继续"，状态存储在 `useWorkflow` store |
| Knowledge 仅服务 Writing | `retrieveKnowledgeContextForGeneration()` 仅在 `/api/generation/writing/route.ts` 中调用 |
| Strategy Output 直接喂给 Writing | `strategyData` 作为 `runWriting()` 的 `strategy` 参数传入 |

### 3.3 Current Prompt Structure

```
SYSTEM: 你是一个内容策略师 + 9 条要求 + JSON format instruction

USER:
  主题：{topic}
  选定角度：
    - 标题：{selectedAngle.title}
    - 切入角度：{selectedAngle.angle}
```

**最适合 Knowledge Context 注入的位置**：在 `{sourceStr}` 之后、`目标平台` 之前。

## 5. Human Approval Boundary

### 5.1 AGENTS.md §10 要求

```text
以下步骤必须支持 Human Approval：
  Angle Selection
  Content Strategy
  Final Draft
Agent 不得默认跳过。
```

### 5.2 真实 UI 层实现状态

| 审批步骤 | 真实位置 | 实现状态 | 说明 |
|----------|----------|----------|------|
| **Angle Selection** | `/create/angles/page.tsx` | ✅ UI 层已实现 | 用户手动选择角度 → `setSelectedAngle()` → 点击"继续"进入 generate |
| **Content Strategy** | `/create/generate/page.tsx` | ⚠️ 隐式缺失 | Strategy 生成后立即执行 Writing，无显式审批步骤 |
| **Final Draft** | `/create/refine` + "保存项目" | ✅ 已实现 | 用户可编辑并主动保存 |

### 5.3 设计结论

**Content Strategy 的 Human Approval 需要在 P0.3.8 流水线中显式设计**：

```
Recommendation:
  Knowledge Context
      ↓
  Strategy Proposal (with evidence markers)
      ↓
  ⚠️ EXPLICIT Human Review / Approval Gate    ← 必须新增
      ↓
  Approved Strategy → immutable after approval
      ↓
  Writing
```

**已批准 Strategy 的稳定性原则**：
- 一旦用户批准 Strategy，后续 Knowledge Retrieval 结果变化不得自动修改已批准 Strategy
- 重新规划必须由 User explicitly requests regeneration 触发
- 同样的稳定性原则适用于已批准的 Angle

## 7. Problem Statement

### 7.1 当前问题

Knowledge Context 仅服务 Writing 层，导致：

| 问题 | 影响 |
|------|------|
| **Strategy 纯想象驱动** | Content Strategy 的 hook、structure、emotionalArc 完全基于 LLM 想象，无历史知识证据支撑 |
| **Angle 选择无知识参考** | 角度生成时无法参考"哪些钩子/结构模式在过去被验证过" |
| **知识价值仅体现在文字层** | Writing 拿到 Knowledge 时已是最终成文阶段，无法影响上游决策 |
| **Strategy 与 Writing 信息不对称** | Writing 有 Knowledge Context，Strategy 没有，两者信息不一致 |

### 7.2 产品层面影响

当 Knowledge Base 包含已验证的 hook pattern、structure pattern 时，如果 Strategy 层无法利用：
- 策略师不知道"Question-based Conversational Hook"在类似主题上有 4 条验证证据
- 策略师不知道"Concept-Naming Insight Structure"的 abstract_pattern 是 "Concept Naming → Contrast Definition → Progressive Revelation"
- 策略提案缺乏知识依据，纯粹是 LLM 的自由发挥

## 8. Strategy Layer Opportunities

### 8.1 Knowledge 对 Strategy 的价值

**问题回答**：Knowledge 可以帮助 Strategy 发现历史高表现模式。

具体价值：

| Knowledge 类型 | 对 Strategy 的价值 | 示例 |
|----------------|-------------------|------|
| `strategic_pattern` | 最高价值 — 直接提供"怎么做内容"的模式 | "用年龄标记建立过来人身份权威" → Strategy 的 emotionalArc 可参考 |
| `hook` + `structural_pattern` | 高价值 — 验证过的钩子模式 | "Question-based Conversational Hook" → Strategy 的 hook 设计有据可依 |
| `structure` | 高价值 — 已验证的内容结构 | "Concept-Naming Insight Structure" → Strategy 的 structure 可复用 |
| `emotion` | 中高价值 — 情感共鸣模式 | 如何引导目标情绪，有证据参考 |
| `cognition` | 中等价值 — 认知偏差/思维模式 | Strategy 论证逻辑可参考 |
| `perspective` | 中等价值 — 视角选择参考 | 哪些角度被验证有效 |
| `language` | 低价值（策略层不涉及具体语言） | 更适合 Writing 层 |
| `surface_technique` | 低价值（表层技巧） | 更适合 Writing / Human Expression 层 |
| `human_expression` | 不适合策略层 | 明确属于 Expression Layer |

### 8.2 Strategy 只需要什么？

**最小信息集合**（非完整 Knowledge Context）：

```
对 Strategy 有价值的字段：
  ✅ name                    — 模式名称（作引用）
  ✅ text                    — 知识内容（作参考）
  ✅ category                — 分类（判断是否与当前策略相关）
  ✅ knowledgeLevel          — 知识层级（判断抽象程度）
  ✅ status                  — validated/candidate（判断可信度）
  ✅ confidence              — 知识库原始置信度
  ✅ similarity              — 与当前主题的相关性

对 Strategy 价值较低的字段：
  ⚠️ evidenceCount           — 证据数量有参考价值
  ❌ evidence                — 完整证据对策略层过载
  ❌ retrieval metadata      — 检索内部信息无需暴露
  ❌ knowledgeId             — 内部 ID 无需暴露
```

## 9. Angle Layer Opportunities

### 9.1 设计判断

**Knowledge Context 是否应该直接推荐 Angle？**

答案：**不应该直接推荐**。

理由：
1. Angle Generation 是**创意发散**过程 — 需要多样性
2. Knowledge 是**收敛证据** — 倾向于推荐已知有效的模式
3. 直接推荐会**扼杀角度多样性** — 总是推荐相似角度

更合理的关系：

```
KnowledgeContext
      ↓
提供历史相关知识（模式/结构/钩子）
      ↓
LLM 在发散时可以参考这些模式
      ↓
生成的角度仍然保持多样性，但有知识参考
```

### 9.2 补充方案：Angle Ranking 辅助

未来可在 Angle Generation 之后增加：

```
Angle[] (generated)
      ↓
KnowledgeContext 模式匹配
      ↓
补充每个 Angle 的相关知识引用（不改变排序）
      ↓
UI 显示"此角度有 N 个已验证模式支持"
```

**本阶段不实现**，仅记录。

## 10. Candidate Policy

### 10.1 三方案对比

#### Option A：Strategy 只看到 validated

| 维度 | 评估 |
|------|------|
| 实现复杂度 | 低（retrieval 层 `include_candidates=false`） |
| Prompt 噪音 | 最低 |
| 信息量 | 仅 15 条 validated KU（较少但可靠） |
| 风险 | 极低（所有知识经过验证） |
| 缺陷 | 丢失 candidate 中的潜在价值模式 |

#### Option B：Strategy 看到 validated + candidate，明确标注

| 维度 | 评估 |
|------|------|
| 实现复杂度 | 中（需区分展示） |
| Prompt 噪音 | 中（多 9 条 candidate，需标注） |
| 信息量 | 全部 24 条 |
| 风险 | 低（Serializer 已经有 `Status:` 区分） |
| 缺陷 | Candidate 可能误导 Strategy |

#### Option C：Strategy 看到全部，但 Prompt 层严格约束

| 维度 | 评估 |
|------|------|
| 实现复杂度 | 高（需额外 prompt engineering） |
| Prompt 噪音 | 高（区分逻辑更复杂） |
| 信息量 | 全部 |
| 风险 | 中高（LLM 可能忽视约束） |
| 缺陷 | 违反"P0.3.7 不新增 LLM Query Rewrite"原则 |

### 10.2 推荐方案

**推荐 Option B**（validated + candidate，Serializer 明确标注 Status）。

理由：
1. **复用 P0.3.7.4 Serializer** — 已经有 `Status: validated` / `Status: candidate` 显式区分，无需额外 prompt 工程
2. **知识库规模小** — 仅 24 条 KU（9 candidate），不会造成 Prompt 过载
3. **LLM 能理解 Status 区分** — 即使在 Strategy 层，LLM 也能可靠地区分 "validated" vs "candidate"
4. **Candidate 有策略参考价值** — 即使是 candidate 的 hook pattern 模式，也能给策略设计提供灵感

**补充约束**：未来 Prompt Assembly 中增加一行：
```
"Candidate knowledge is unverified and should be used as inspiration only, not as confirmed fact."
```

## 12. Recommended Architecture

### 12.1 推荐完整链路

```
Topic (User Input)
      ↓
Retrieval #1: Strategy Knowledge
  Query: topic + topicProfile.keywords.join(' ')
  Builder: buildKnowledgeContext(response, { maxItems: 5 })
      ↓
Strategy Knowledge Context
  → serializeKnowledgeContext(ctx)
  → inject into Strategy Prompt (between sourceStr and platform)
      ↓
Content Strategy Proposal
  title, hook, structure, keyArguments, emotionalArc, CTA, tone
  + Knowledge Context Block in prompt as evidence
      ↓
⚠️ HUMAN APPROVAL GATE (Strategy Review)    ← 必须新增
  User can: Accept / Modify / Regenerate
      ↓
APPROVED Strategy (immutable until explicit regeneration)
      ↓
┌──────────────────────────────────────────────────┐
│ Retrieval Decision:                              │
│   IF strategy.query ⊇ writing.query:             │
│     → reuse Strategy KnowledgeContext           │
│   ELSE:                                          │
│     → Retrieval #2: Writing Knowledge            │
│       Query: topic + selectedAngle + strategy.hook│
│       Builder: buildKnowledgeContext(response)   │
│       → Writing KnowledgeContext                │
└──────────────────────────────────────────────────┘
      ↓
Writing
  → serializeKnowledgeContext(writingCtx)
  → inject into Writing Prompt
      ↓
Draft
      ↓
⚠️ HUMAN APPROVAL (Final Draft Review)
      ↓
Expression Layer
  → human_expression KUs injected
      ↓
Final Output
```

### 12.2 Retrieval 策略

| 阶段 | Query 公式 | maxItems | 说明 |
|------|-----------|----------|------|
| Strategy Retrieval | `topic + topicProfile.keywords` | 5 | 宽泛检索，覆盖策略层需要的模式 |
| Writing Retrieval | `topic + selectedAngle + strategy.hook` | 5 | 精确检索（现有 P0.3.7.5 逻辑） |
| 复用条件 | Strategy.query ⊇ Writing.query | — | 如果 Writing 的 query 信息已被 Strategy 覆盖，可复用 |

**简化推荐（P0.3.8 阶段）**：不使用复用逻辑，Strategy 和 Writing 分别执行 Retrieval。
- 理由：实现简单，query 各自独立优化，避免复用导致的信息损失
- 代价：2 次 embedding API call（约 400ms 额外延迟）

## 13. Recommended Contract（数据契约设计）

### 13.1 方案对比

#### 方案 A：直接复用 KnowledgeContext

```typescript
// skills/content-strategy/schema.ts
export const contentStrategyInputSchema = z.object({
  // ... existing fields
  knowledgeContext: z.custom<KnowledgeContext>().optional(),
})
```

| 维度 | 评估 |
|------|------|
| 实现复杂度 | 低（零新增类型） |
| 类型统一 | ✅ 复用 P0.3.7.2 contract |
| 边界清晰度 | ❌ Strategy 能看到不必要信息 |
| Prompt 噪音 | 中（Serializer 输出对策略层有冗余字段） |

#### 方案 B：建立 StrategyKnowledgeContext View

```typescript
// src/knowledge/context/strategy-knowledge-context.ts
export interface StrategyKnowledgeContext {
  query: string
  patterns: StrategyPattern[]    // 从 KnowledgeContext 精选
  constraints: { hasCandidates: boolean, wasTruncated: boolean }
}

export interface StrategyPattern {
  name: string
  text: string
  category: KnowledgeCategory
  knowledgeLevel: KnowledgeLevel
  status: KUStatus
  confidence: ConfidenceLevel
  similarity: number
}
```

| 维度 | 评估 |
|------|------|
| 实现复杂度 | 中（新增 1 个 View 类型 + 1 个转换函数） |
| 类型统一 | 需要从 KnowledgeContext → StrategyKnowledgeContext 转换 |
| 边界清晰度 | ✅ 明确只为 Strategy 服务 |
| Prompt 噪音 | 低（只暴露策略层需要的字段） |

### 13.2 推荐方案

**推荐方案 A（直接复用 KnowledgeContext）**。

理由：
1. **不要提前引入复杂 Context Factory** — AGENTS.md §26 原则
2. **Serializer 已经提供足够抽象** — `serializeKnowledgeContext()` 输出已过滤敏感字段
3. **Strategy 需要的字段 ⊆ Writing 需要的字段** — 策略层需要的 name/text/category/status/confidence/similarity 在现有 Serializer 中全部存在
4. **未来如果确实需要不同 View 再重构** — 数据层 Adapter 容易添加，不要提前设计

**约束**：P0.3.8 实现时必须保持 KnowledgeContext contract 不变，Strategy 层通过 Serializer 消费。

```
  选定角度：{selectedAngle details}
  {profileStr}                              ← topicProfile
  {audienceStr}                             ← audienceInsights
  {personaStr}                              ← persona
  {sourceStr}                               ← 原始素材
  ## Knowledge Context                      ← ✅ INJECT HERE (after sourceStr)
    ### Primary Knowledge N: ...
    ### Supporting Knowledge N: ...
    ### Retrieval Metadata
  目标平台 / 内容类型 / 期望语调 / 目标字数
  反虚构警告 + 人设指令
```

### 14.2 位置选择理由

1. **在 sourceStr 之后** — 原始素材是事实基础，Knowledge 是补充证据，逻辑顺序正确
2. **在平台/字数之前** — 这些是约束条件，放在最后作为"落地指令"
3. **与 Writing Prompt 保持一致** — P0.3.7.5 Writing 中是 `originalContent → KnowledgeContext → platform`，Strategy 中是 `sourceContent → KnowledgeContext → platform`

### 14.3 Block 大小估计

根据当前 Knowledge Base 数据估算：
- 5 条 Knowledge Items × ~80 字/条 = ~400 字
- Retrieval Metadata = ~60 字
- **总计约 460 字** — 对 Strategy Prompt 长度影响可控

## 15. Human Approval Safety（防绕过机制）

### 15.1 必须满足的约束

```
AGENTS.md §10 — Knowledge Context 不能绕过 Human Approval

禁止：
  Knowledge → 自动替换 → 已批准 Strategy

必须：
  Knowledge → Strategy Proposal → 用户审批 → 锁定
```

### 15.2 设计方案

```typescript
// 未来数据结构（设计，不实现）
interface StrategyState {
  proposal: ContentStrategy        // AI 生成的策略提案
  status: 'draft' | 'approved' | 'regenerating'
  knowledgeContextId: string        // 关联的 Retrieval 版本
  approvedAt?: number               // 审批时间戳
}

// 安全规则
function canUpdateStrategy(
  current: StrategyState,
  newKnowledge: KnowledgeContext | null
): boolean {
  if (current.status === 'approved') return false  // 已批准 → 不可自动更新
  if (current.status === 'regenerating') return true // 重新生成中 → 可以
  return true  // draft 状态 → 可以
}
```

### 15.3 Retrieval 变化检测

即使 KnowledgeContext 发生变化：

| 当前状态 | Knowledge Context 变化时行为 |
|----------|------------------------------|
| `draft` | 允许重新检索并更新提案 |
| `approved` | ❌ 不允许自动更新，保持原策略 |
| `regenerating` | 使用最新 Retrieval 结果 |

| 网络超时 | null → 纯 LLM | null → 纯 LLM |
| Retriival 返回 0 结果 | Empty Context block | Empty Context block |

## 18. Empty Context（空结果处理）

### 18.1 定义

`retrieval success + 0 result` — Retrieval 服务正常工作但没有匹配到任何 Knowledge Unit。

### 18.2 处理方式

**推荐与 P0.3.7.5 保持语义一致**：

| 情况 | 行为 |
|------|------|
| `null`（Retrieval 失败） | `knowledgeContext: undefined` — Prompt 中不注入任何 Knowledge block |
| `KnowledgeContext with selectedCount=0` | Serializer 输出 `"No relevant knowledge was retrieved."` — 注入 Placeholder block |

Strategy Prompt 中空 Knowledge 的处理：

```typescript
const knowledgeText = knowledgeContext
  ? serializeKnowledgeContext(knowledgeContext)
  : ''  // Retrieval failure → 不注入任何内容

const sourceAndKnowledge = sourceStr + (knowledgeText ? `\n${knowledgeText}` : '')
```
