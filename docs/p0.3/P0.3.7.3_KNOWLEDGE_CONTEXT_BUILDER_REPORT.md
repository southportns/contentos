# P0.3.7.3 — Knowledge Context Builder Report

## 1. Status

**COMPLETE**

## 2. Objective

KnowledgeContextBuilder transforms SemanticRetrievalResponse into KnowledgeContext — deciding which retrieved Knowledge should enter the Generation Context and how it should be organized.

Core function: `buildKnowledgeContext(response, options?) → KnowledgeContext`

## 3. Architecture

```
SemanticRetrievalResponse
        ↓
KnowledgeContextBuilder
  1. Map results → KnowledgeContextItems
  2. Detect candidate presence
  3. Sort (status → similarity → confidence → evidence → knowledgeId)
  4. Apply maxItems limit
  5. Classify primary / supporting
  6. Build evidence traceability
  7. Construct constraints & metadata
        ↓
KnowledgeContext
```

## 4. Selection Rules

| Dimension | Rule | Source |
|-----------|------|--------|
| Candidate handling | Keep candidates if present in response | Response detection |
| Status priority | validated (0) < candidate (1) | Deterministic sort |
| Similarity | Higher first | Preserved from retrieval |
| Confidence | Higher first via CONFIDENCE_SCORES | Existing mapping |
| Evidence count | More first | Derived from KU.evidence |
| maxItems | DEFAULT_TOP_K (5) | P0.3.6 production config |

## 5. Primary / Supporting Rules

**Deterministic Rule-Based Classification:**

- Items ≤ 3: ALL primary, none supporting
- Items ≥ 4: `floor(n × 0.6)` primary (capped at 4, minimum 1), rest supporting
- Classification happens AFTER truncation

Example distributions:
| Total | Primary | Supporting |
|-------|---------|------------|
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 3 | 0 |
| 4 | 2 | 2 |
| 5 | 3 | 2 |
| 6+ | floor(n×0.6) | remainder |

## 6. Evidence Traceability

For each selected Knowledge Item:
1. Look up full CanonicalKnowledgeUnit from response
2. Iterate evidence.items
3. Create KnowledgeContextEvidence by mapping:
   - `knowledge_id` → `knowledgeId`
   - `quote` → `quote` (original, unmodified)
   - `evidence_id` → `evidenceId`
   - `content_id` → `contentId`
   - `validation` → `validation`
   - `evidence_quality` → `quality`
   - `evidence_trust` → `trust`
4. Deduplicate by evidenceId (Map)

Traceability chain preserved: Generated Content → KnowledgeContext → knowledgeId → Evidence → contentId → Original Content

## 7. Empty Context

When retrieval returns zero results:
- `selectedCount = 0`
- `primaryKnowledge = []`
- `supportingKnowledge = []`
- `evidence = []`
- `constraints.hasCandidates = false`
- `constraints.wasTruncated = false`
- `metadata.version = "1.0.0"`

No exceptions thrown. No knowledge fabrication.

## 8. Determinism

- Sorting uses stable criteria chain: status → similarity → confidence → evidenceCount → knowledgeId
- Tie-breaker: `knowledgeId.localeCompare()` ensures consistent ordering
- No `Math.random()`, no dependency on object iteration order
- Same input + same config → identical output (except `metadata.createdAt`)

## 13. Known Limitations

1. **Retrieval metadata gap**: `SemanticRetrievalResponse` does not carry the actual `threshold` and `topK` values used. Builder uses `DEFAULT_SIMILARITY_THRESHOLD` and `DEFAULT_TOP_K` as recorded values, which matches production configuration but does not record per-request overrides.

2. **includeCandidates detection**: Builder detects candidate presence by scanning results for `status === 'candidate'`. This is consistent with retrieval default behavior (candidates excluded when `include_candidates=false`) but does not perfectly distinguish "caller chose to include candidates" from "candidates slipped through due to retrieval bug".

3. **Text reconstruction**: Builder reconstructs knowledge text from KU fields (mirroring `buildEmbeddingText` in `semantic-index.ts`) rather than extracting from the embedding index. This produces the same text but duplicates the concatenation logic.
