# P0.3.7.5 — Generation Layer Integration Report

## 1. Status

**COMPLETE**

## 2. Objective

Formally connect the P0.3.7.4 Knowledge Context Serializer into the existing Generation / Prompt Assembly flow:

```
KnowledgeContext
        ↓
serializeKnowledgeContext()
        ↓
knowledgeContextText
        ↓
Generation Prompt Assembly
        ↓
LLM
```

From this stage onward, the Writing generation pipeline consumes validated knowledge as an independent prompt block.

## 3. Architecture

```
User Input (topic + selectedAngle)
        ↓
API Route /api/generation/writing (Orchestration Layer)
        ↓
retrieveKnowledgeContextForGeneration(query)
        1. Semantic Retrieval (existing singleton, production defaults)
        2. KnowledgeContextBuilder (P0.3.7.3)
        ↓
KnowledgeContext            (retrieval failure → null → pure LLM, never blocked)
        ↓
runWriting({ ...input, knowledgeContext })   (Skill — business logic)
        ↓
WRITING_PROMPT(..., knowledgeContext)        (Prompt Assembly)
        ↓
serializeKnowledgeContext(knowledgeContext)  (P0.3.7.4 — the ONLY formatter)
        ↓
Knowledge Context Block (independent prompt section)
        ↓
generateText() → LLM (unchanged call)
```

Architecture follows the P0.3.7.1 Reconnaissance §8.1 decision:
**API Route orchestration + Retrieval Service + Context Builder + Skill consumer**.

## 5. Prompt Behavior

**Block position** (existing prompt content unchanged, knowledge inserted between original-material section and platform line):

```
主题 / 选定角度 / 内容策略 / 结构大纲        ← existing (unchanged)
创作人设 / 受众洞察 / 表达蓝图              ← existing (unchanged)
原始素材                                  ← existing (unchanged)
## Knowledge Context                      ← NEW (P0.3.7.4 serializer output)
  ### Primary Knowledge N ...
  ### Supporting Knowledge N ...
  ### Retrieval Metadata ...
目标平台 / 目标字数 / 最终指令             ← existing (unchanged)
```

| Behavior | Handling |
|----------|----------|
| validated | `Status: validated` explicit, never converted |
| candidate | `Status: candidate` explicit, never converted, never filtered |
| empty context | Serializer placeholder `No relevant knowledge was retrieved.` injected; prompt assembles normally; generation never blocked |
| retrieval failure | Orchestration returns `null` → `knowledgeContext: undefined` → prompt is byte-identical to pre-integration behavior (pure LLM) |
| wasTruncated | Only source is `KnowledgeContext.constraints.wasTruncated` via serializer; generation layer never recomputes |
| retrieval internals | `threshold`/`topK`/`retrievalReason`/`knowledgeId`/timestamps stay inside the knowledge module; generation layer never touches them (enforced by TEST 11 source inspection) |

## 11. Design Decisions

1. **Writing-only integration**: The content-strategy skill is a Human Approval-gated decision step (AGENTS.md §10). This stage integrates only the final Writing generation — the single "现有 LLM Generation" entry. Strategy-side knowledge injection is deferred to a later stage to keep this stage minimal and reversible.
2. **Skill receives KnowledgeContext (not text)**: The P0.3.7.4 serializer is called inside Prompt Assembly (`prompts.ts`), satisfying "Generation Layer must call serializeKnowledgeContext" and keeping serialization out of the API route.
3. **Graceful degradation returns `null` (not empty context)**: A retrieval *failure* is semantically different from a retrieval with *zero results*. Zero results → real empty KnowledgeContext → serializer placeholder injected. Failure → null → pre-integration prompt (byte-identical).
4. **include_candidates=true at orchestration**: candidates enter the context explicitly labeled `Status: candidate`, consistent with the P0.3.7.2 contract's candidate-preservation design. No filtering, no conversion.
5. **Retrieval query formulation**: deterministic string join `topic + angle.title + angle.angle` — no LLM query rewriting in this stage.

## 12. Known Limitations

1. **Per-request embed call**: each writing request performs 1 embedding API call for the query (P0.3.2-3 design: exactly 1 `embed()` per search). Knowledge-side vectors are loaded from persistence (0 API calls).
2. **No query cache**: repeated identical topics re-embed. A search-level cache already exists in douyin tooling but is out of scope here.
3. **Strategy / angle skills do not receive knowledge yet** — see Design Decision 1.
