## 1. Purpose

在 Strategy 自动注入 Knowledge 辅助生成后，确保人类在 Strategy 进入 Writing 阶段之前有一次**显式审查机会**。这是 retreival-augmented generation pipeline 的**最后一道人工安全防线**。

**核心设计原则**：
- Knowledge is **advisory, not authoritative** — 模型可以参考知识，但人类做最终决策
- Approval gate 必须**零侵入** — 如果用户跳过/忽略，已有流程保持不变
- State 持久化在 localStorage（browser-side）— 页面刷新后审批状态保留
- **服务器端审批状态是 Source of Truth** — 客户端无法绕过审批直接进入 Writing（P0.3.8.4.1）

## 3. State Design

### 3.1 StrategyApprovalState (Client-side)

```typescript
type StrategyApprovalStatus = 'none' | 'pending' | 'approved' | 'rejected'

interface StrategyApprovalState {
  status: StrategyApprovalStatus
  knowledgeAssisted: boolean   // 是否经过 Knowledge 检索
  reviewedAt: number | null    // 最后审批时间戳
  approvedStrategy: ContentStrategy | null  // 最终批准的策略
}
```

### 3.2 Server-side Approval State (Source of Truth)

```prisma
model ContentStrategy {
  // ... existing fields ...
  approvalStatus   String   @default("pending") // pending | approved | rejected
  rejectionReason  String?
  approvedAt       DateTime?
  rejectedAt       DateTime?
}
```

### 3.3 State Transitions

```
       ┌──────────────────────────────────────────┐
       │                                          │
       ▼                                          │
    [none] ──setStrategyPending──→ [pending]      │
                                    /        \     ️
                             approve       reject  │
                              /            \      │
                             ▼              ▼     │
                      [approved]      [rejected]──┘
                          │            (regenerate:
                          │             reset→pending)
                          ▼
                    Writing + Eval
                          │
                        [done]
```

### 3.4 Actions

| Action | Transition | 说明 |
|--------|-----------|------|
| `setStrategyPending(knowledgeAssisted)` | none → pending | Strategy 生成后调用 |
| `approveStrategy(editedStrategy?)` | pending → approved | 用户通过审批（可传入编辑后的策略） |
| `rejectStrategy()` | pending → rejected | 用户拒绝，准备重新生成 |
| `resetStrategyApproval()` | any → none | 重置所有审批状态 |

## 6. P0.3.8.4.1 — Server-side Approval Enforcement

### 6.1 Purpose

**防止客户端绕过 UI 审批直接调用 Writing API**。服务器端数据库中的 `approvalStatus` 字段是唯一真相来源（Source of Truth），API 层强制检查此状态。

### 6.2 安全威胁模型

| 威胁 | 攻击路径 | 防御机制 |
|------|---------|---------|
| UI 绕过 | 用户修改 React state 跳过审批 UI | Writing API 从 DB 加载 `approvalStatus`，不信任客户端请求体 |
| API 绕过 | 直接调用 `/api/generation/writing` 不带审批 | Writing API 检查 `strategyId` 对应的 DB 记录状态 |
| 状态注入 | 客户端请求体中注入 `approvalStatus: 'approved'` | Zod schema 不包含此字段；即使手动传入也会被 `sanitizeInput` 剥离 |
| 并发竞争 | 同一策略被同时 approve 和 reject | Prisma `updateMany` + `where: { approvalStatus: 'pending' }` 条件更新保证原子性 |

### 6.3 条件更新实现（防止竞争条件）

```typescript
// topic-repository.ts
async approveStrategy(strategyId: string): Promise<boolean> {
  const result = await prisma.contentStrategy.updateMany({
    where: { id: strategyId, approvalStatus: 'pending' },
    data: { approvalStatus: 'approved', approvedAt: new Date() },
  })
  return result.count > 0
}
```

**关键设计**：
- `updateMany` 的 `where` 子句包含当前状态条件
- SQLite 单写器保证同一时刻只有一个写操作生效
- 返回 `count: 0` 表示状态已被其他请求修改 → 返回 `false` 表示操作失败

### 6.4 Writing API 门禁逻辑

```typescript
// writing/route.ts — P0.3.8.4.1 Gate Check
if (isDatabaseConfigured()) {
  const strategy = await safeDb(
    () => contentService.getStrategyById(input.strategyId),
    'writing-gate-check',
  )

  // 策略不存在 → 拒绝 (missing = not approved)
  if (!strategy) {
    return NextResponse.json(
      { success: false, error: 'STRATEGY_NOT_APPROVED' },
      { status: 403 },
    )
  }

  // 策略存在但未批准 → 拒绝
  if (strategy.approvalStatus !== 'approved') {
    return NextResponse.json(
      { success: false, error: 'STRATEGY_NOT_APPROVED', currentStatus: strategy.approvalStatus },
      { status: 403 },
    )
  }
}
```

### 6.5 Approve/Reject API 设计

#### POST `/api/generation/strategy/approve`

```json
// Request
{ "strategyId": "strat_001" }

// Response (200)
{ "success": true, "data": { "strategyId": "strat_001", "approvalStatus": "approved" } }

// Error (409) — 状态已被修改
{ "success": false, "error": "INVALID_TRANSITION", "currentStatus": "rejected" }

// Error (404) — 策略不存在
{ "success": false, "error": "STRATEGY_NOT_FOUND" }
```

#### POST `/api/generation/strategy/reject`

```json
// Request
{ "strategyId": "strat_001", "reason": "Not aligned" }

// Response (200)
{ "success": true, "data": { "strategyId": "strat_001", "approvalStatus": "rejected", "reason": "Not aligned" } }

// Error (409) — 状态已被修改
{ "success": false, "error": "INVALID_TRANSITION", "currentStatus": "approved" }
```

### 6.6 输入消毒（Input Sanitization）

```typescript
// 剥离客户端可能注入的 approvalStatus 字段
const sanitizeInput = (input: Record<string, unknown>) => {
  const { approvalStatus, ...safe } = input
  return safe
}
```

即使客户端在请求体中传入 `approvalStatus: 'approved'`，该字段在 Zod 解析前被剥离，服务器只根据 DB 状态做转换。

## 8. Safety Guarantees

### 8.1 Knowledge 不影响审批
- Knowledge 仅作为 Strategy 生成的上下文辅助
- 人类审批是最终决策，Knowledge 无法自动通过策略

### 8.2 Graceful Degradation
- 如果 localStorage 损坏，刷新页面后 `strategyApproval` 回到初始值 `none`
- 用户可以通过重新生成获得新策略
- 如果数据库未配置（`isDatabaseConfigured() === false`），Writing API 跳过审批检查（开发环境降级）

### 8.3 State Machine Integrity
- `approveStrategy` 只能在 `pending` 状态下生效（前端 + 后端双重保证）
- `rejectStrategy` 后自动清除 downstream 数据（通过 `clearDownstream` 保证一致性）
- 数据库层条件更新保证并发安全

### 8.4 Server-side Enforcement (P0.3.8.4.1)
- 客户端请求体中的 `approvalStatus` 被 Zod schema 拒绝 + `sanitizeInput` 剥离
- Writing API 通过 `strategyId` 从 DB 加载状态，不信任客户端提供的任何状态信息
- 缺失策略默认拒绝（missing = not approved, never default-approve）
- approve/reject API 使用条件更新，同一状态只能被一个请求成功转换
