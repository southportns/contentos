# P0.5.2 — Draft Version History & Restore Integration

## Status: IN_PROGRESS

## Overview

P0.5.2 wires together existing Version History UI and Restore infrastructure
(created in P0.4.x) with the Active Draft Editor (P0.5.1) to deliver:

1. **Version History** — Clear, sorted display with Active Draft indicator
2. **Restore** — Safe historical version restore with cross-tab notification
3. **Integration** — Seamless connection between Editor ↔ Version History ↔ Restore

**Core Principle**: Restore never modifies history — it creates a new Draft.

## 3.1 Current State

### Draft Data Model

```
model Draft {
  id            String   @id @default(cuid())
  topicId       String
  version       Int      @default(1)    ← Monotonic, unique per topic
  parentDraftId String?                 ← Self-relation for lineage
  changeType    String   @default("INITIAL")  ← INITIAL|RESTORE|MANUAL_EDIT|REGENERATE|REFINE|HUMANIZATION|OTHER
  changeReason  String?                 ← Human-readable reason
  title         String?
  content       String
  outline       Json?
  status        String   @default("DRAFT")
  wordCount     Int?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@unique([topicId, version])          ← Prevents duplicate versions
  @@index([parentDraftId])
}
```

### Active Draft (Topic)

```
model Topic {
  id           String   @id @default(cuid())
  activeDraftId String?  @unique         ← Points to current working draft
  activeDraft   Draft?   @relation("TopicActiveDraft")
  drafts        Draft[]
  ...
}
```

**Active Draft 含义**: The designated "current working version" that:
- Editor binds to for editing
- `changeType` operations (Manual Edit, Restore) create children from
- Cross-tab sync broadcasts when changed

### P0.5.1 Manual Edit Workflow

```
User edits active draft → isDirty=true → Click Save
  ↓
saveManualDraftEdit(sourceDraftId, content, title)
  ↓
[Server-side OCC: sourceDraft.topic.activeDraftId === sourceDraft.id]
  ↓ (throws ACTIVE_DRAFT_CONFLICT if stale)
prisma.$transaction {
  1. Re-read max version
  2. Create new MANUAL_EDIT draft (version++)
  3. Update Topic.activeDraftId = newDraft.id
}
  ↓
broadcastActiveDraftChange() + router.refresh()
```

## 3.3 Version Chain Example

```
v1 AI_GENERATE
  │
  └── v2 MANUAL_EDIT (parent = v1)
       │
       └── v3 MANUAL_EDIT (parent = v2)
             │
             └── v4 RESTORE (parent = v1)   ← 内容来自 v1，但遵循 P0.4 语义
                    │                          parentDraftId = source draft
                    └── v5 MANUAL_EDIT (parent = v4)
```

**Important**: The existing `createRestoredDraft` sets `parentDraftId: sourceDraft.id`
(the draft being restored, not the current active draft). This is the P0.4 semantics
— preserved as-is per P0.5.2 requirements.

**Reason**: parentDraftId tracks WHERE the content came from, NOT which version was
active when Restore was clicked. This is meaningful for lineage tracing.

## 3.6 Restore OCC Analysis

### Does `createRestoredDraft` need the same OCC as `createManualEditDraft`?

**No.** Here's why:

| Aspect | Manual Edit | Restore |
|--------|-------------|---------|
| Source | Active draft (must be current) | Historical version (intentionally old) |
| Semantic | "Edit the current thing" | "Go back to an old thing" |
| OCC concern | Stale active = overwrite risk | No stale concern |
| Conflict handling | ACTIVE_DRAFT_CONFLICT check | P2002 retry (version uniqueness) |

**Example scenario**:
- Tab A: active = v3, Restores v1 → creates v4 (RESTORE), active = v4
- Tab B: active = v3 (stale view), Restores v1 → P2002 caught → retry → creates v5 (RESTORE), active = v5

This is **correct behavior**: Both tabs intentionally chose to restore v1. Each
gets a unique version. The last writer wins on activeDraftId, which is acceptable
because both operations were explicit user intents.

### Cross-Tab Protection for Restore

The existing P0.4.9 `useActiveDraftSync` handles this:
- Tab A Restores → broadcasts `(v4)` → Tab B receives
- Tab B (clean): router.refresh() → shows v4
- Tab B (dirty): amber banner → user decides

The broadcast AFTER restore (Step 3) completes this loop.
